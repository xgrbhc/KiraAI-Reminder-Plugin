# 提醒保存与调度一致性修复

状态：代码修复、隔离回归与用户重启后的正常操作验收已完成（2026-10-04）。用户已授权分析后直接实施。范围对应检测报告 R1、R2；不包含 R3 自主状态并发覆盖。

## 目标与边界

- 只有保存和调度都完成，才返回创建、编辑、恢复等成功结果。
- 保存失败时，不改动原运行任务。
- 调度失败时，补偿已完成的本次调度变更，并回滚本次文件变更；补偿失败必须明确报错，不能承诺已全部回滚。
- 随机批次作为一次变更处理，不保留半批成功任务。
- 重要删除保持原确认和权限检查；文件/调度失败不提前丢弃 WebUI 删除令牌。
- 只改插件；不改主项目、提示词、时间语义、权限与投递重试策略，不增加用户输入步骤或额外依赖。

## 实现选择

1. 扩展现有 `ReminderStorage.modify()`：提供可选同步 `after_save` 回调。在同一存储锁内先原子保存，再调用回调；回调失败则恢复旧数据。普通存储调用维持原行为。
2. 插件内共享调度变更回调：比较旧/新提醒，仅处理本次变化的任务；先登记新增/更新，再移除删除/暂停目标。编辑直接使用既有 `replace_existing=True`，不先移除原任务。
3. 调度动作按相反顺序补偿；使用 APScheduler 公开 Job 字段保存原运行快照，恢复时保留 trigger、args、next_run_time 等，避免重设间隔相位。登记/移除已生效但随后抛错也检查并补偿。任务已不存在的移除属于幂等成功，其他移除失败不能静默吞掉。
4. `ReminderScheduler.add_job()` 对调度器不存在或注册异常抛出明确错误，让调用者阻止成功返回。
5. 真实确认所用存储包装器转发回调，目标检查仍在锁内。通用服务和自主跟进的提醒文件变更复用同一保护；自主意图状态文件不在本轮改成跨文件事务。

检查过主项目 `core/utils/` 的原子文件/更新事务接口；现有更新事务面向应用文件替换，不适用于内存调度。本轮复用插件已有原子 JSON 保存，不引入核心更新事务依赖。

## 保证范围

- 调度回调同步执行，不在存储锁内等待网络、LLM 或异步发布。
- 单进程普通异常点可补偿；不能把内存调度与 JSON 文件称为跨进程、断电安全的强原子事务。
- 调度器持续故障或回滚时再次发生磁盘错误，可能使补偿不完整；明确返回失败并记录日志，保留文件原子写入保护，要求检查后重载，不自动重投真实提醒。
- 实际 APScheduler 使用公开运行快照恢复；不依赖其私有 jobstore。简化测试替身没有 get_job 时才按原记录补偿。不能承诺恢复未公开的内部字段或已经执行的任务，但本轮不执行任何发布/LLM 动作。
- 自主跟进的提醒文件与意图索引是两个文件，本轮不承诺两者强原子提交；旧快照覆盖问题留到 R3。

## 验收

- 创建、编辑、暂停、恢复、删除、重要删除和随机批次的正常行为保持一致。
- 注入保存失败，确认文件和原运行任务不变、没有新任务登记。
- 注入登记失败，确认不返回成功、不保留半批创建；失败编辑保留原提醒/原任务。
- 注入批量移除失败，确认已移除目标恢复、文件回滚。
- 注入补偿自身失败，确认错误明确、不假报完整恢复。
- 群聊确认仍检查目标快照和原权限；本轮不改任何工具描述或动态提示文本。
- 对应审计观察转换为断言期望行为的常规回归测试，并更新审计脚本说明。
