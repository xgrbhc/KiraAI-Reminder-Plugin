# 自主状态并发覆盖修复方案（R3）

状态：代码修复、隔离回归与用户重启后的简单使用验收已完成（2026-10-04）。修复基线为插件提交 `ebc3b8f`；实施时未修改主项目、提示词或真实数据。版本记录以插件 Git 历史为准，本轮不推送。

## 1. 问题与证据边界

修复前的 `autonomy.py` 有四处以 `load_state()` 取得数据，修改后通过 `_autonomy_storage.save(state)` 保存整份旧快照：每日自检、到期跟进兜底、随机计划生成、随机自检。其中每日／到期／随机自检会等待事件发布；随机计划路径没有等待外部发布，但分离读取与保存仍不是完整读改写事务。

2026-10-04 在当前提交上重新运行每日自检的隔离探针：暂停假发布回调，创建新意图，再恢复回调；意图数量从 1 变成 0。测试中的 `1 passed` 表示缺陷成功复现，不能解释为已经修复。

主项目核对结果：`core/event_bus.py` 的 `publish()` 只等待事件入队，`core/lifecycle.py` 当前创建无容量上限的队列；通常入队不会主动挂起，也不等待 LLM 完成。因此，探针证明的是“发布或存储等待期间实际发生交错修改时，旧快照会覆盖新数据”。没有证明当前默认运行必然产生该交错，也没有从用户日志确认实际丢失。不能把整个模型响应时间都视为覆盖窗口。

本轮定位为小范围可靠性修复：消除这种保存方式对异步实现和锁竞争的脆弱依赖，不扩大为主项目消息处理故障。

## 2. 核心规则

- 旧快照只用于挑选候选和构造本轮事件，不能在处理结束后整份保存。
- 使用既有 `ReminderStorage.modify()`，在同一锁内读取最新状态，仅更新本轮拥有的字段；保留意图列表、其他会话和未知字段。
- 发布事件必须在存储锁外；锁内不等待模型、网络或其他异步发布。
- 只对成功发布的本轮结果写回元数据；发布失败不标记完成，不自动重新发布。
- 已关闭、暂停、删除或改排的目标不能被旧结果复活、还原或清空新安排。
- 不增加用户输入或确认步骤，不改变自主规划频率、权限、策略或提示词。

已检查主项目 `core/utils/`；不需要新的核心依赖。复用插件现有锁和原子文件保存，不引入数据库、跨进程锁、版本号迁移或通用事务框架。

## 3. 四条路径的改法

| 路径 | 本轮允许写回的字段 | 处理方式 |
| --- | --- | --- |
| 每日自检 `daily_cycle_job()` | 会话 `last_cycle_at` | 成功发布后在最新状态上更新当前会话，不保存旧意图列表 |
| 随机自检 `random_check_job()` | 会话 `last_random_check_at`、`last_random_check_scheduled_at` | 成功发布后短事务更新，不覆盖同时发生的每日记录或意图修改 |
| 到期兜底 `followup_due_job()` | 目标意图 `last_followup_at`、`last_followup_source`、`updated_at`，及符合下述条件的 `next_check_at`、`next_check_job_id` | 按意图 ID 定位最新目标，核对本次到期安排，不覆盖标题、备注、优先级和状态 |
| 随机计划 `schedule_random_checks()` | 会话 `random_check_plan_date`、`random_check_window`、`random_check_times` | 在短事务中读取最新状态、生成／复用计划及执行现有同步任务登记；不再独立保存整份旧快照 |

随机计划保持原时间生成算法、每日次数、窗口、任务 ID、触发器与复用规则。锁内不调用异步发布；同步调度登记沿用现有调用顺序。本轮不为自主随机检查任务新增调度补偿事务，也不宣称计划文件与运行调度强原子一致。

### 到期跟进的必要保护

1. 从初始快照取得候选意图 ID，以及本次 `next_check_at`、`next_check_job_id`。
2. 发布每个候选前，重新核对目标仍存在、状态允许跟进、到期安排未变，并核对对应自主提醒是否已存在；失效候选跳过。这样前一个事件等待期间的修改也不会被后续候选直接忽略。
3. 锁外发布事件。
4. 发布成功后再次从最新状态定位同一目标。只有目标仍允许跟进且上述两个安排字段仍匹配，才写本轮跟进元数据并清空这次已处理的安排。
5. 如果期间已安排新跟进，或者目标暂停／关闭／删除，跳过本轮目标回写；保留最新状态，不复建旧目标。标题或备注变化不阻止有效元数据更新，但这些内容必须原样保留。

会话元数据写回也检查当前会话是否停用。原本存在而期间被删除的会话不重建；首次运行、尚无会话记录时仍允许按既有规则创建默认状态。同一检查元数据按成功处理完成顺序更新，不额外定义新的优先级或时间排序策略。

## 4. 修改边界

预计业务改动集中在 `autonomy.py`，必要时加入小型内部复用方法；常规并发回归放入 `tests/test_autonomy_consistency.py`。不为文件行数拆出新的服务层。

- `create_intent()`、`update_intent()`、`close_intent()`、`mark_followup_fired()` 已使用锁内读改写，本轮不顺带重写其业务规则。
- `schedule_intent_followup()` 已在最新状态上更新字段，不属于整份旧快照保存。本轮验证“新安排不被兜底清空”，不承诺解决它与关闭意图之间所有跨文件竞态。
- R4 参数无效却部分保存、R5 普通随机提醒分钟重复、R6 嵌套损坏保护、重复提醒开始日期语义，继续独立处理。
- 不修改主项目、适配器、缓存、历史消息、默认／自定义／动态提示词、工具描述、前端或配置格式。不自动重启或推送；提交须用户授权。

本方案不提供跨进程／断电安全事务，也不提供事件恰好一次处理保证。发布后发生关闭或保存失败，不能撤回已入队事件；本轮只保护后续状态写回，不通过自动重发掩盖失败。事件发布成功也不等于 LLM 或平台投递已经确认成功。

## 5. 轻量验收

使用临时文件和假发布回调，以 `asyncio.Event` 控制交错顺序，不靠随机 sleep 碰运气，不操作真实提醒或真实 LLM：

- 每日／随机自检等待期间创建意图，完成后新意图仍存在。
- 等待期间编辑标题、备注、优先级及状态，旧任务不能覆盖这些修改。
- 到期跟进等待期间安排新检查，新时间和 job_id 保留；普通到期成功仍清空原安排。
- 目标暂停、关闭、删除或已有自主提醒时，不写回失效结果，也不复活目标。
- 多会话同时修改、每日与随机记录交错，相关字段和未知数据保留；首次无文件的正常行为保持。
- 发布等待期间，其他意图操作可以完成，证明未持有存储锁等待发布；发布失败不能写完成记录。
- 随机计划在等待存储锁期间发生意图修改，最终计划与新意图同时保留；原调度契约不变。

实施时将显式审计脚本的 R3 观察转换为“新意图保留”的安全断言，并同步报告说明。完成后执行相关测试和插件 Python 全套；没有前端改动，不要求重复浏览器操作或用户手工制造并发故障。

用户只需实施后重启，按平常方式简单使用自主意图／跟进即可。特殊交错由自动测试覆盖，不增加常规体验中的流程。
