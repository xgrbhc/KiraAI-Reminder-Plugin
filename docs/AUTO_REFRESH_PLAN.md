# 提醒看板轻量自动刷新方案

日期：2026-10-04。基线：`cead49d`（窄屏与长内容修复已提交）。状态：周期自动刷新经收益／复杂度讨论暂缓，尚未实施；用户确认的“手动扫描同步会话和用户名单”已实施，见第 7 节。第 1–6 节保留此前的轮询设计，不能当作全部获准或已完成。

## 1. 目标与边界

LLM 新增／编辑提醒、提醒到期或投递状态变化后，已打开的看板能在数十秒内更新，不必每次手动扫描。不追求严格实时，不增加用户确认步骤。

只调整插件前端及测试，继续使用现有桥接和接口。不改主项目、插件 Python 业务、鉴权、数据格式、调度、提示词或 LLM 缓存；不增加 WebSocket、SSE、依赖、后台服务或配置迁移。保留手动“扫描网络”作为即时更新与失败恢复入口。

## 2. 源码分析：不能直接加一个定时器

| 当前实现 | 直接定时调用的影响 | 必须调整的边界 |
| --- | --- | --- |
| `fetchReminders()` 设置 `loading=true`、清空 `loadedSessionId` | 每轮都会禁用操作按钮，影响正常使用 | 后台读取与前台加载状态分开 |
| 读取失败清空列表并弹通知 | 网络波动会使列表消失、滚动变化，周期性通知可能刷屏 | 后台失败保留上次列表，明确标记过期并禁用写操作，不连续弹通知 |
| 刷新先关闭会话下拉框 | 可能打断输入或选择会话 | 输入框聚焦、下拉框打开时跳过自动轮次 |
| `fetchSessions()` 只在初始化调用 | 手动扫描也不更新会话下拉列表及用户名单 | 辅助元数据低频更新，手动扫描时同步更新 |
| 有会话／请求序号检查，但没有轮询协调 | 手动读取、后台读取、弹窗与写操作可能竞争 | 前台优先；旧后台结果不能覆盖确认或写操作后的状态 |
| `readApi()` 用 12 秒超时竞争 Promise | 超时不代表底层 GET 已取消 | 超时后停止自动新请求，不能一直堆叠底层未结束的请求 |

主要位置：`web/app.js` 的 `fetchReminders`、`fetchSessions`、`readApi`、`openModal`、`runMutation` 和生命周期；`web/index.html` 的加载、错误与禁用状态。

### 必须明确：“只读”不是后端零写入

前端自动刷新只发送 GET，不发送暂停、恢复、重试、忽略或删除等 POST。

但现有 `main.py:api_get_deliveries` 会调用 `DeliveryTracker.reconcile()`：它可能把超过现有 5 分钟等待阈值的记录标为未确认，为历史逾期的一次性提醒补记未确认记录，或清理已确认／已忽略且与原快照一致的一次性提醒。这是现有查询和运行流程已有的对账行为，不会重新投递、调用 LLM 或执行 `action`。

建议保留现有接口语义，并在说明中称为“前端仅 GET 的状态刷新”，不承诺后端完全不写文件。若要求查询绝对不写任何数据，需要另行设计插件后端接口，不纳入本方案。

## 3. 建议默认行为

### 刷新频率与条件

| 场景 | 建议 |
| --- | --- |
| 有已加载的有效会话 | 每轮结束约 30 秒后读取当前投递状态和提醒，共两个 GET |
| 会话列表／用户名单 | 最多约 60 秒更新一次；不扫描其他会话的完整提醒列表 |
| 页面没有已加载会话 | 仅低频更新会话列表，不根据正在输入的 ID 自动查询提醒 |
| 手动扫描／选择会话／写操作完成 | 保留即时读取；成功后重新计时，不再紧接一次自动读取 |
| 确认框、令牌输入、写请求、前台加载、会话输入或下拉选择 | 暂停自动发起和应用结果；不排队补做每个错过的轮次 |
| 浏览器标签隐藏、页面离开或组件卸载 | 停止自动发起；返回后过期了才补一次，并受上述条件限制 |

默认自动启用，不新增设置面板或开关。正常情况下每个打开且可见的看板约不超过 5 个自动 GET／分钟；手动操作额外产生现有读取。多标签页会分别读取，不声称存在跨标签页统一限流。现有接口会读取 JSON 文件并对账，因此不能承诺完全没有 CPU／磁盘开销。

使用“本轮结束后再安排下一次”的单个 `setTimeout`，不使用不等待请求完成的 `setInterval`，避免慢请求排队。浏览器也可能推迟计时，所以 30 秒是建议间隔，不是严格实时保证。[MDN：轮询计时与请求完成顺序](https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval)

页面可见性使用 `visibilitychange`，同时处理 `pagehide`／`pageshow` 和卸载。当前主项目通过 iframe 展示插件，未提供专门的可见性桥接；标签隐藏可检测，但宿主仅通过 CSS 隐藏 iframe 不会触发其文档可见性变化。不要为补足这一特殊情况访问或改写主项目 DOM；此类宿主隐藏方式不承诺停止轮询。[MDN：Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)、[pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event)

### 正常更新不打断操作

- 后台读取不清空列表、不关闭下拉框、不显示全页加载占位，不周期性禁用按钮。读取过程中仍使用上次完整成功快照；前端数据不是跨客户端事务锁，写操作仍由后端校验。
- 保留当前会话、用户筛选、键盘焦点和滚动位置；同会话相同结果不重复替换数组。筛选用户已无提醒时显示现有空筛选状态，不擅自切回全部用户。
- 当前会话两个读取都成功后，一次性提交前端结果；先读投递状态，再读提醒，减少现有对账清理后仍显示旧一次性提醒的情况。两个 API 不是数据库事务快照，不能承诺期间完全没有外部变化。
- 新增或移除真实卡片可能自然改变页面高度；不锁死滚动，不恢复已经失效的旧位置。
- 会话列表是辅助元数据：它单独失败时保留旧名单并提示未更新，不让已成功取得的当前提醒列表不可操作。

### 失败与恢复

- 后台提醒／投递读取失败时，保留上次完整列表；显示简短的“上次读取结果／自动更新失败”状态，并禁用写操作。涉及投递状态的实时判断显示未知，不能把旧记录当作新确认的状态。
- 已结束的失败读取可退避重试：第一次失败后约 60 秒、第二次约 120 秒；第三次连续失败后暂停自动刷新，保留手动扫描恢复。不自动重试任何写操作，不每轮弹通知。
- 辅助会话列表采用独立失败计数；连续三次失败后只暂停其自动更新，不拖停正常的当前会话读取。
- 12 秒逻辑超时不能取消桥接底层 GET。超时后暂停自动刷新，保留手动扫描入口；手动重试也要合并重复点击，不能由定时器反复开新请求。晚到结果失效，不覆盖新状态。
- 写请求结果不明时，保留现有“刷新核对后再操作”的保护。自动读取不能悄悄解除保护或宣称写操作成功；需要显式手动扫描成功后恢复。
- 初次加载、切换会话及手动扫描的失败处理保留现有明确错误语义；新“保留旧快照”仅适用于同会话后台刷新，不把其他会话数据当作当前数据。

## 4. 实现结构与范围

复用现有读取、响应校验、会话与请求序号检查，抽出共享的快照读取／提交路径；不要复制两套接口和校验逻辑，也不要为两个定时频率建立通用任务框架。

- `web/app.js`：后台刷新状态、过期状态、手动恢复保护、一个轮询计时器和读取协调。手动请求优先；打开确认、开始写入、编辑会话、隐藏或卸载时使旧后台响应失效。提交前再次核对会话、代次及交互状态。
- `web/index.html`：仅增加简短状态提示，区分前台加载、后台刷新与过期数据；不新增确认框。
- `web/i18n.js`：新增状态提示同步中英文；这是界面文案，不涉及 LLM 提示词。
- `tests/test_dashboard.js`／隔离服务器：假计时、延迟读取、失败和可见性测试，不连接真实提醒或模型。
- 本地资源和维护文档：如增加 Tailwind 类，重新构建并提交实际变化的产物。

当前 `PluginPageContext.api.get` 没有 AbortSignal 参数；不绕过桥接直接 fetch，不修改主项目桥接或认证来强行取消请求。生命周期停止新增请求并忽略晚到响应，不声称已取消所有底层网络请求。

新计时器使用独立句柄并纳入清理，不能把通知消失计时器一起停止。清理应可重复调用；卸载后不再更新 UI、弹通知或安排新轮次。

## 5. 轻量验收

开发者以隔离测试完成以下重点，不要求用户逐项操作：

1. 模拟外部新增提醒和投递状态变化，自动更新列表／计数／用户名单；自动路径只发 GET。
2. 正常轮询期间按钮可用、列表不清空；在列表中部仍保持合理位置，筛选不变。
3. 输入、下拉选择、确认框、令牌输入和写请求期间，自动轮次不干扰；之前已发起的后台结果不能覆盖操作状态。
4. 会话切换、手动优先、慢请求、逻辑超时及晚到响应不串会话、不重复轮询；不宣称逻辑超时已取消 HTTP。
5. 后台失败保留列表但标记过期并禁用写操作；辅助名单失败不误禁用有效快照；退避、暂停、手动恢复不刷屏。
6. 隐藏／返回及卸载没有遗留新轮次；写结果不明的保护不会被自动成功读取解除。既有确认、通知、滚动和资源测试继续通过。

无需为验证调用真实 LLM 或发送提醒。用户只需加载新版后留意一次正常使用产生的提醒变化是否自动显示，手动扫描仍可用即可。

## 7. 当前取舍与最小改进

用户询问复杂度与收益后，决定暂缓周期刷新：现有普通操作已经更新当前列表，定时读取的主要收益是展示外部变化，但需要额外处理输入、弹窗、隐藏、超时与写结果不明等状态。本轮不增加轮询计时器、退避、可见性监听、后台恢复或设置面板。

用户明确了解并认可“手动扫描同时更新会话和用户名单”后，实施这一独立子项：

- 扫描按钮与输入框 Enter 并行读取会话元数据及当前提醒／投递，保留会话与用户筛选。无会话时仅能取得名单，缺少 ID 的原提示保持不变。
- 使用既有桥接、超时和错误文案，不新增依赖、接口、提示词或样式类。保留现有投递 GET 的对账语义，不查询平台联系人或实时昵称。
- 一次扫描结束前合并重复触发；名单失败保留旧值，不使有效提醒不可操作。初始化旧名单及卸载后的响应失效，不声称已取消底层 GET。
- 普通写操作成功后的刷新仍只更新当前会话，不新增全量名单请求。
