# 插件前端窄屏与长内容适配方案

日期：2026-10-04。分析基线：`33b332d`。状态：用户已确认，布局修复已实施并通过隔离验证；用户简单运行后反馈“没什么大问题”，不代表全部手机场景已验证。实施记录见第 6 节。

## 1. 结论与边界

建议做一次小范围布局修正，不重做页面、不增加操作步骤。保留现有桌面风格、按钮大小、确认流程及通知策略。

本轮只涉及插件 HTML、CSS、本地构建产物、隔离测试和维护文档；不修改主项目、Python 业务、API、权限、调度、数据格式、认证、提示词或 LLM 输入缓存。不加入新依赖、自动刷新、自动重试或额外确认。

## 2. 修复前的具体检查结果

使用实际插件静态资源，在现有隔离服务器的 iframe 中检查；数据来自内存，不连接 Kira 或 LLM。检查浏览器视口宽度 320、375、768、1280px，并检查 320×480px 的低高度确认框。仅打开及取消确认框，模拟 POST 数始终为 0。

下表中的“内容可用宽度”是 iframe 的 `documentElement.clientWidth`，已扣除本次测试环境的滚动条；不是外层窗口宽度。长内容测试使用合成的连续英文名称、分类、动作名称和长 URL，不代表日常提醒都会这么长。

| 场景 | 实测 | 影响 |
| --- | --- | --- |
| 320px 普通内容 | 内容可用宽度 297px；会话控件宽 344px，右边到 368px；页面 `scrollWidth` 为 368px | 右侧选择会话按钮可能被裁切，交互时还可能发生横向位置调整 |
| 375px 普通内容 | 内容可用宽度 352px；会话控件仍到 368px | 常见窄窗口也存在溢出，不只是极小屏幕 |
| 375px 长内容 | 卡片宽 238px，但标题 `scrollWidth` 为 3840px；分类、姓名、动作名称越过卡片边界 | 提醒正文及状态信息被裁切，标签排列拥挤 |
| 768px 长内容 | 内容可用宽度 760px；文本区宽 3840px，操作按钮右边到 4073px | 切为横排后，按钮被长内容挤出可视区域 |
| 1280px 长内容 | 内容可用宽度 1272px；操作按钮右边到 4085px | 桌面同样受影响，不能只修手机断点 |
| 320px 普通卡片 | 三层横向留白：页面 24px、列表面板 32px、卡片 24px；卡片标题区仅约 130px 宽 | 普通中文也频繁换行，页面显得拥挤 |

### 已确定的原因

- `web/index.html` 的会话输入框为 `w-64`（256px），加上图标、间距、内边距和选择按钮，整体实测宽 344px；会话下拉菜单另有固定 `w-80`（320px）。
- 卡片文本区只有 `flex-1`，缺少 `min-w-0`；标题没有长词换行处理。768px 起横排后，长字符串的最小内容宽度会把操作区推开。
- 标签行没有 `flex-wrap`，长分类没有宽度和换行约束；姓名及动作以裸文本放在 Flex 行内，也没有完整的收缩与换行边界。
- 页面、列表面板和卡片沿用桌面留白，窄屏可读宽度被多次压缩。
- `overflow-x-hidden` 只能隐藏部分溢出，不能让文本和按钮真正适配。不能以“没有横向滚动条”作为修复完成的证据。

Flex 项目的自动最小宽度可能采用最小内容宽度，因此需要允许文本区收缩；长字符串还须配合换行处理。参见 [MDN：min-width](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/min-width)。

### 已能正常工作，不应顺带重写

- 普通提醒在上述宽度的卡片操作按钮均保持 48×48px，暂停／恢复和删除入口可见。
- 长内容重试确认框在 375px 下没有横向溢出；320×480px 时面板高度约 403px、内部内容约 807px，现有纵向滚动有效，取消成功。
- 确认框已有会话 ID 换行、正文换行和基于 `100dvh` 的高度限制。
- 本轮测试页未记录警告或错误；此前来源未明的 MutationObserver 错误不能因此视为已修复。

### 尚未充分验证的风险

- 用户筛选按钮中的超长昵称没有宽度约束；源码存在风险，但本次未单独复现长昵称筛选按钮。
- 通知正文已有换行，但超长标题及低高度下三条长通知的遮挡程度未实测。
- 真实手机软键盘、Safari、主 WebUI 导航栏展开后的组合布局未验证。视口检查不等于所有手机环境认证。

## 3. 建议改法

### A. 会话选择区：随可用空间缩放

- 窄屏会话控件占满当前内容宽度，外层允许收缩；输入框使用 `min-w-0` 和弹性宽度，图标与选择按钮不收缩。
- 扫描按钮在窄屏独立成行；空间充足时恢复当前自然宽度与排列。
- 下拉菜单窄屏跟随控件宽度；较宽屏保留现有约 320px 上限。会话 ID 继续使用现有省略显示，不改真实值、匹配或提交方式。
- 保留会话切换、Enter 扫描、加载中禁用等逻辑，不新增选择步骤。

候选方向：输入框的固定 `w-64` 改为可收缩宽度；下拉菜单改为 `w-full sm:w-80 max-w-full`。外层宽度须一起调整，不能只改输入框一处。

### B. 提醒卡片：正文可收缩，操作区不被挤走

- 文本主区增加 `min-w-0`；操作区增加 `shrink-0`，保留两个 48px 圆形按钮及当前可见性，不改为必须悬停才显示。
- 标题、分类、姓名、ID、动作名称增加有界换行。需要时给元数据文字包一层可收缩的文本元素，图标保持固定大小。
- 标签行允许换行；普通短标签保持紧凑，长分类允许在卡片内多行显示。
- 用户筛选按钮增加最大宽度和昵称换行；不只依靠悬停提示显示全名，不改变筛选身份。
- 正文、状态及动作名称不截断、不修改存储数据；只改变显示布局。

长字符串建议局部使用 `overflow-wrap: anywhere`，而不是给全页加 `word-break: break-all`。前者在正常断点不够时才拆长词，并参与最小内容宽度计算，适合长 URL／ID。参见 [MDN：overflow-wrap](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap)。

### C. 窄屏留白：给内容让出空间

建议使用现有断点，不新增一套手机专用页面：

| 区域 | 窄屏建议 | 较宽屏保留 |
| --- | --- | --- |
| 页面 | `p-4`（16px） | `sm:p-6 md:p-12` |
| 行动清单面板 | `p-4` | `sm:p-8` |
| 提醒卡片 | `p-4 pb-6` | `sm:p-6 sm:pb-8` |
| 统计网格／卡片 | `gap-3`／`p-4`，仍为两列 | `sm:gap-6`／`sm:p-6`，768px 起四列 |
| 异常投递面板 | `p-4` | `sm:p-6` |

不靠缩小按钮或大幅缩小字号换取空间。较宽屏的留白、颜色、阴影和状态线保持原样。

当前 Tailwind 3 的 `sm` 从 640px 开始、`md` 从 768px 开始、`xl` 从 1280px 开始；无前缀样式作为窄屏基础。插件运行在 iframe 内，应以 iframe 可用宽度判断，而不是外层浏览器或设备名称。参见 [Tailwind 3：响应式设计](https://v3.tailwindcss.com/docs/responsive-design)。

### D. 确认框与通知：只做防御性布局调整

- 确认框窄屏可用 `p-4 sm:p-8`，标题文本区允许收缩；关闭按钮适当扩大点击区域，避免与标题重叠。
- 保留现有纵向滚动、Esc、Tab 焦点限制、焦点恢复、重要删除令牌和提交锁；不改变确认次数或文案。
- 通知窄屏适当减少内边距和图文间距，图标及 × 不收缩，标题也允许长词换行。
- 保留最多三条、约四秒、相同内容合并及错误优先级；保留深色实底、无背景模糊、透明关闭按钮和绿／红侧边线。
- 实施时先检查三条长通知在低高度下的实际遮挡。若仍明显遮挡，再单独提出通知列表高度限制；本方案不先行增加内部滚动、截断错误信息或更改自动消失策略。

## 4. 实施范围与顺序

确认后作为一个小任务实施，顺序为：先修会话区及卡片收缩／换行，再调整窄屏留白和弹层细节，最后构建与轻量回归。

预计文件：

- `web/index.html`：布局类、元数据文本包裹和必要的可收缩边界。
- `web/style.css`：局部长字符串换行规则；不写全局强制断词规则。
- `tests/dashboard_server.py`：可选的长内容模拟场景，保持默认测试数据不变，不连接真实接口。
- `tests/test_local_assets.js` 或现有相关测试：保护必要布局约束及构建产物。
- `web/vendor/` 中实际受构建影响的 CSS、资源清单，以及维护／检查文档。

预计不需要修改 `web/app.js` 或翻译文件；若实施发现必须改逻辑或文案，应先说明，不顺带扩展范围。提示词变更仍需单独展示对比并取得确认。

## 5. 轻量验收与维护

开发者完成以下检查即可，不要求用户走复杂流程：

1. 320、375、768、1280px 下检查普通内容和长内容：会话框及菜单不越界，完整正文可换行，标签不越界，操作按钮在卡片内且可见。
2. 看实际元素边界、`scrollWidth` 和最终样式；不能只检查生成的类存在，或只看页面横向滚动条。
3. 低高度下打开并取消一个长内容确认框；检查必要文字和按钮能通过滚动访问，取消不发送写请求。顺手检查通知及绿／红／黄状态线。
4. 修改 Tailwind 类后在 `web/` 执行 `npm run build`，再运行 `node --test tests/test_dashboard.js tests/test_local_assets.js`。当前既有 Node 基线为 41 项，此数字不是本次重新运行结果。
5. 构建后重新加载隔离页面再检查；保留当前样式顺序，不能再次让通用面板规则覆盖工具类。

布局变更确实会改变换行、卡片高度，不能要求新旧布局的绝对滚动像素相同；但普通操作刷新仍应沿用已有保留列表与焦点恢复逻辑，不能重新引入每次操作回到顶部的问题。

用户验收只需按原部署方式重载／重启后 Ctrl+F5，在窄窗口顺手查看会话框和一条提醒，再打开／取消确认框即可。不为此改动真实提醒内容，不必人为创建超长任务。
