## 1. 目标与约束

本轮目标是让提醒插件的入口、业务逻辑、持久化和后台任务各有清晰归属，降低修改时跨越整个 `main.py` 的成本；同时保持现有功能和对外行为。重构完成后，应能从一个业务入口追踪“校验身份与参数 → 修改数据 → 更新调度 → 返回结果”，而不需要分别理解 Web API、快捷命令和 Tool 的实现细节。

**结构重构与功能修复分开提交。** 已知的混合消息批次鉴权、损坏 JSON 覆盖、到期投递确认、随机任务数量限制等问题需要修复，但修复会改变运行语义；它们应各自有针对性的测试和独立变更。重构阶段可以添加暴露问题的测试并标记为后续修复项，不应悄悄改变权限、投递或存储策略。安全问题的修复优先级不因结构重构而降低。

### 本轮不改变的契约

| 契约 | 必须保持的内容 |
| --- | --- |
| 插件识别与加载 | `manifest.json` 的 `plugin_id=reminder_plugin`、`core_version`；`main.py` 中唯一的 `BasePlugin` 主类；相对导入和热重载可用。版本号仅在正式发布时按发布流程调整。 |
| 生命周期 | `initialize()`/`terminate()` 对调度器、健康任务、注册资源的现有可观察行为；配置变更后的重新初始化。 |
| LLM 扩展 | 全部 14 个 Tool 的名称、参数 schema、描述和返回文本；3 个 Hook 的事件类型、优先级及提示词插入顺序；页面注册信息。若发现基线数量不符，以自动登记快照为准。 |
| HTTP 与页面 | `GET /sessions`、`GET /reminders/{session_id}`、`POST /reminders/confirm-delete`、`POST /reminders/{action}` 的路径、默认认证、请求/响应形状；`/dashboard`、菜单标签及 `PluginPageContext` 的使用。 |
| 人类快捷命令 | 现有唤醒前缀、别名、序号映射、响应文字和拦截行为。产品层面的命令调整单独设计。 |
| 配置与数据 | `schema.json` 键、默认值及 `advanced_config` 层级；`data/config/plugins/reminder_plugin.json`；`data/plugin_data/reminder_plugin/{reminders.json,autonomous_state.json}` 的字段、时间格式、job ID 和迁移路径。既有数据不因纯重构而批量重写。 |
| 调度 | APScheduler 3 的触发器类型、时区/本地时间解释、补发/过期处理、重试次数、确认令牌有效期及自主循环频率。需要修正这些行为时另立功能变更。 |
| 依赖 | 不增加运行时第三方依赖，不要求更改 KiraAI 核心或其他插件。 |

上表中的“保持”是重构验收基准，并非认定当前行为没有缺陷。例如 `/r all` 的现有语义及存储损坏处理已在审查中指出问题，但不能在搬移代码时顺手改掉。

## 2. 当前结构与目标结构

现状：`main.py` 同时定义配置模型、时间工具、JSON 存储、后台调度、自主意图、Web API、快捷命令和 LLM Tool；`identity.py`、`permissions.py` 已有独立边界；`web/index.html` 集中模板、样式和脚本。当前测试主要覆盖身份/权限和部分存储迁移，入口之间的一致性尚未锁定。

目标目录（按职责拆分，不为了文件数而拆分）：

```text
KiraAI-Reminder-Plugin/
├── main.py                 # BasePlugin、生命周期、Hook/Tool/API/Page 装饰器薄入口
├── config.py               # ReminderConfig、默认值与旧配置归一化
├── models.py               # Reminder/Intent 的类型定义及持久化边界校验
├── identity.py             # 现有主体识别；本轮仅迁移必要调用
├── permissions.py          # 现有纯权限判定；本轮仅迁移必要调用
├── storage.py              # 原子 JSON 读写及事务接口
├── reminder_service.py     # 提醒用例：增删改查、标记、暂停/恢复、确认令牌
├── scheduler.py            # 触发器、恢复、健康检查与到期投递编排
├── autonomy.py             # 自主意图状态、周期检查与跟进编排
├── manifest.json
├── schema.json
├── requirements.txt
├── web/
│   ├── index.html
│   ├── app.js              # 页面行为；仍使用原 PluginPageContext bridge
│   └── style.css           # 页面样式
└── tests/
    ├── conftest.py         # 统一的插件加载与假对象夹具
    ├── test_contracts.py   # 装饰器登记、API、配置、持久化契约
    ├── test_reminder_service.py
    ├── test_scheduler.py
    └── test_autonomy.py
```

这不是要求一次提交完成的文件清单。若某模块抽出后只有少量无复用代码，可暂时保留在相邻模块；`models.py` 先用 `TypedDict`/枚举描述当前 JSON 形状，不在重构阶段强制把所有旧记录转换为新对象。Web 资源拆文件仅移动代码，不改界面或引入构建链。

### 依赖方向

`main.py` 负责装配 `config → storage → service → scheduler/autonomy`，并把 KiraAI 事件转换为业务调用。`reminder_service.py` 不导入 FastAPI、页面代码或 APScheduler 的具体触发器；调度通过小接口或回调传入。`storage.py` 不导入 KiraAI 事件、调度器或权限模块。`identity.py`、`permissions.py` 保持可独立测试的纯逻辑。`scheduler.py` 与 `autonomy.py` 通过构造参数协作，不相互导入对方的实现类，避免循环依赖。

工具、Hook、API 和 Page 的**装饰器方法留在 `main.py`**，内部委托给服务。KiraAI 当前在模块导入时用函数所属模块识别插件并登记组件；把装饰器直接移至子模块可能改变登记归属。主项目实现见 [`plugin_registry.py`](https://github.com/xxynet/KiraAI/blob/28ec1064e2edf3749128e90d21a14b8f0b9a0e29/core/plugin/plugin_registry.py)。同理，`main.py` 继续导出唯一的 `ReminderPlugin(BasePlugin)`；新增类不继承 `BasePlugin`。

## 3. 关键接口设计

1. **入口层**：`main.py` 的装饰器签名和返回类型保持原样。入口只做事件到业务上下文的映射、调用服务、把结果转换成原有文本或 JSON。初期可以让服务直接返回原有字符串，以降低差异；结构化 `Result` 和统一错误码放在后续独立变更中。
2. **请求上下文**：新增轻量 `ReminderRequestContext`，包含 `sid`、现有 `PrincipalContext`、群聊/艾特等已解析信息。只能通过现有 `IdentityResolver` 和事件方法构造；本轮不得重新定义“谁是发起人”。混合消息批次的鉴权修复属于独立安全变更。
3. **服务层**：所有提醒写操作通过同一服务入口调用现有 `permissions.py` 规则。Web API 可以继续使用当前可信 Web 主体映射，快捷命令继续使用当前事件映射；重构时通过测试确保同一操作在三种入口下的授权结果一致。
4. **存储层**：保留 `load/save/modify` 对外方法、路径、编码、JSON 键与原子替换形式。重构阶段仅移动实现并加测试；文件损坏时改为拒绝写入、同步 I/O 改异步/SQLite 等是后续行为或性能变更。
5. **调度层**：从服务接收已验证的提醒对象，负责注册/取消 job；到期处理通过注入的发送回调调用当前 KiraAI 事件机制。避免在服务与调度器间互相 import；由入口装配。此阶段不改变“入队视为成功”的既有语义。
6. **自主循环**：拥有 `autonomous_state.json` 的业务操作和周期 job；普通提醒的创建、删除仍调用共享服务。先迁移方法位置，不重新设计状态机或自动动作权限。

## 5. 编码与审查规则

- 新代码注释用英文，解释“为什么”而非复述代码；面向用户的提示文字保持原文。项目 AGENTS.md 的 WebUI 中英文本同步规则继续适用。
- 新增 Python 代码统一使用 Python 3.10+ 类型写法（如 `list[str]`、`dict[str, Any]`）；边界字段以 `TypedDict`/枚举或现有 Pydantic 配置模型描述，不在业务代码里新增无说明的字符串键。
- 模块顶层不启动调度器、不读写用户数据；副作用只发生在生命周期或显式服务调用中。构造函数不承担新数据迁移。
- 避免新增“通用工具箱”或只包一层的抽象；只有明确消费者和可测试契约时才提取接口。移出的代码保持调用顺序与异常行为，后续再单独处理宽泛 `except Exception`、文本错误码等问题。
- PR/提交说明列出“搬移了什么、保持了什么、如何验证”。若后续创建 PR，遵循主项目 `.github/PULL_REQUEST_TEMPLATE.md`；插件仓库若有自己的模板，优先遵循插件仓库模板。

## 6. 完成定义与后续工作边界

结构重构完成时，`main.py` 应主要是插件适配层；业务规则集中在服务层；存储与调度可在不启动 KiraAI 的情况下测试；当前对外契约和历史数据仍可用；全量相关测试与一次本地加载/重载检查通过。**行数减少本身不是验收标准**，可追踪的数据流和入口一致性才是。

下列事项另开变更并分别审查：修复审查报告中的安全/可靠性问题；修改 `action_policy` 或自主模式语义；变更提醒数据格式或迁移策略；改造到期回执与补发；更换持久化后端；引入前端构建链、外部资源本地化或界面重新设计；修改人类快捷命令及提示词。它们可按风险优先穿插实施，但不要和纯搬移代码合成一个难以回滚的提交。
