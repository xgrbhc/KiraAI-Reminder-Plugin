# 插件前端维护注意事项

## 适用范围

只维护插件自身的 HTML、CSS、JS 和本地资源。不得因界面优化修改主项目、提醒权限／调度、认证或 LLM 输入缓存；涉及提示词仍须先展示修改对比，由用户确认后修改。不要为视觉检查操作真实提醒。

## 样式顺序不能随意调整

当前 `web/index.html` 的样式表顺序为：

1. Outfit 字体。
2. Font Awesome 图标。
3. `style.css`：页面背景、面板默认样式及特殊效果。
4. `vendor/tailwind.min.css`：元素明确指定的颜色、边框、圆角和阴影等工具类。

这里让同等优先级的 Tailwind 工具类覆盖通用面板默认值。**不要把 `style.css` 移到 Tailwind 后面**，否则 `.glass-panel` 中的通用 `border`、`border-radius`、`box-shadow` 会盖掉彩色侧边线、圆形按钮和独立阴影。HTML 中 class 名称的先后顺序不能解决 CSS 覆盖问题。

明确的特殊规则仍可有更高优先级，例如 `.glass-panel.toast-panel` 保持通知深色实底、禁用背景模糊；键盘焦点样式也要保留。当前方案没有把自定义 CSS 纳入构建，直接改 `style.css` 仍不需要重新构建。若以后重做样式分层，须同时更新构建脚本、此说明及测试，不能只调文件顺序。

## 保护状态标记

- 成功通知：4px 绿色左边线；错误通知：4px 红色左边线。
- 重要提醒：4px 黄色左边线；普通提醒保留透明左边线。
- 投递异常区域及确认弹窗：黄色半透明边框。
- 暂停／恢复／删除按钮：保持圆形；通知关闭按钮保持透明背景和可见键盘焦点。
- 通用悬停规则不要用 `border: ...`、`border-color: ...` 或左侧边框规则覆盖状态标记。卡片只提亮上、右、下三条边，不改变左边线的颜色或宽度。

## 构建与分发

- 新增／修改 Tailwind 类时用完整名称，不用字符串拼接制造类名；扫描配置覆盖 `index.html`、`app.js`，新增含样式类的源码文件时同步调整配置。
- 修改这些类、Tailwind 配置／输入文件或前端依赖后，在 `web/` 执行 `npm run build`。首次准备环境或锁文件变化后先执行 `npm ci --ignore-scripts --cache ./.npm-cache`。
- 直接修改 `style.css`、文字／翻译、未涉及样式类的 JS 逻辑，不需要前端构建。后端重载／重启与前端构建是两件事。
- 不手改 `vendor/`。提交生成资源、源配置、锁文件和许可证；不提交 `node_modules/`、npm 缓存。保留 `.gitattributes` 对资源字节的保护。
- 运行时只引用插件内相对资源路径；不要重新引入外部 CDN、额外 npm 运行要求或主项目静态路由。

## 轻量回归检查

资源文件存在、样式类已生成、测试通过，**不等于最终样式一定正确**。修改资源引入方式、加载顺序或通用面板规则后，至少检查上面几类实际显示效果，包含卡片悬停和键盘焦点；不需要完整遍历全部功能。

在插件目录运行：

```bash
node --test tests/test_dashboard.js tests/test_local_assets.js
python tests/dashboard_server.py --port 0
```

测试服务器输出本机地址：主页面使用内存模拟提醒；地址后加 `/style-probe` 打开无 API 的固定样式检查页。该页面从实际 `index.html` 提取样式表顺序，便于复查绿／红／黄色边框、圆形按钮、阴影、悬停及焦点，不会改真实数据。

不要只凭代码判断；用浏览器读取最终样式或对照截图。检查后停止测试服务器。真实部署按原方式重载／重启，再 Ctrl+F5 刷新即可。

事故及修复记录见 [前端检查记录](FRONTEND_REVIEW.md)；资源版本和许可见 [本地资源说明](../web/THIRD_PARTY_NOTICES.md)。

## 窄屏与长内容检查

布局修改须同时检查窄 iframe 和长名称／URL／分类／动作，不仅检查普通短文字。允许文本区收缩并换行，不能靠 `overflow-x-hidden` 隐藏超出页面的按钮或内容；操作按钮及状态标记仍须可见。实际 iframe 宽度决定响应式断点，外层窗口宽度不等于插件可用宽度。

本次布局修复及验证见 [窄屏与长内容适配方案](RESPONSIVE_LAYOUT_PLAN.md)。长字符串使用局部 `.content-wrap`，Flex 文本区同时保留 `min-w-0`；不要删掉元数据的可收缩文本包裹，也不要让操作区收缩。短文字测试通过不能代替长内容检查。

重复提醒的日期区域须分别显示“开始”和“下次”；下次缺失显示后端状态，不能退回到 `task.time`。仅在查询／扫描等已有刷新时更新。隔离服务器支持 `?recurring=1&sid=Test%3Adm%3Aalice`，加入 `&locale=en` 可检查本次新增英文标签；确认窄 iframe 下时间行可换行、按钮不被挤出。此次复用已有样式类，无需重构建；以后若新增类，仍按上述构建规则执行。

隔离服务器支持 `?sid=Test%3Adm%3Aalice&list_size=3&stress=1` 长内容场景，默认数据不变。通知的横向适配与纵向遮挡是不同问题；低高度下多条超长通知的高度策略仍待单独确认，不要顺带截断错误内容或改变计时。

## 投递时间不能使用提醒开始日期

待处理投递的“触发时间”读取本条实际尝试记录的 `created_at`，不能使用提醒快照的 `time`、提醒创建时间或状态更新的 `updated_at`。`legacy_unconfirmed`／零次尝试／无可靠时间只显示“原定时间”和“实际触发时间未知”，不能把补建账本时间伪装成触发时间。

重复任务合并的 `latest_due_at` 单独显示为“最近周期触发”；它不表示又投递了一次，也不能覆盖原投递的触发时间。不改写数据或进行浏览器时区换算。中英文标签须同步。此修复复用已有样式类，不需要重构建本地资源。

隔离服务器支持 `?sid=Test%3Adm%3Aalice&delivery_times=1`，可再加 `&locale=en`；仅使用虚构任务，检查正常记录、旧补建和合并周期记录。实施与模型可见文本的确认边界见 [投递时间显示修复方案](DELIVERY_TIME_DISPLAY_PLAN.md)。

## 投递记录与原待办分开处理

投递区只提供“忽略此次”，不可重新添加 retry／defer 按钮或私自调用旧接口。确认框必须说明：忽略只处理投递问题，不删除原待办、不改变周期计划、不撤回动作。Tool／API 与页面行为保持一致，中英文同步。

历史异常不等于周期任务停用，活动数不能再简单排除 pendingJobIds。保留的过期单次任务使用后端只读派生字段 is_overdue_once 展示“已过期（保留）”并排除活动数；此字段不可写回提醒配置。页面忽略后必须验证原待办仍在，不能只检查异常数下降。隔离预览的模拟 API 同样不得删除原任务，其桥接脚本已有 Node 语法和行为测试。
