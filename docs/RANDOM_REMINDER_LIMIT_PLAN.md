## 1. 实施前的问题与证据

- `time_utils.determine_random_count` 没有独立数量上限；固定次数非正数可能退回默认 1 次，单独提供区间端点会被忽略，参数错误不够明确。
- `generate_multiple_random_times` 按时间范围估算容量，范围越长可生成的数量越大。例如未来一年请求 50 万次，当前容量计算允许生成 50 万个时间点。
- `ReminderService.set_reminder` 同步生成、排序时间点；随后在存储事务内逐条创建记录、登记调度任务，并返回完整时间列表。大量任务可能占用事件循环、存储锁、内存及模型输入。
- 群聊确认后的创建仍走同一个服务，确认不构成数量上限，也不能作为绕过资源保护的授权。
- 自主随机检查是另一项能力，`random_check_daily_count` 已限制到每天 0~3 次，不应与用户随机提醒混为一谈。

证据来自本地代码检查；没有实际创建 50 万条任务，也没有进行生产压测。检查 `core/utils/` 未发现可直接复用的这类批次数量校验。

## 2. 已确认规则

1. 单次新建随机提醒批次最多 **100 条**。这是建议的初始产品边界，不是已证明的机器性能阈值；第一版采用插件内部常量，不增加配置项或用户确认步骤。
2. 固定次数或随机区间超过上限时，整个请求直接拒绝，写入和调度登记均为零；不偷偷截成 100 条，不让管理员或 LLM 确认绕过。
3. 有效次数必须为正整数；布尔值、字符串、小数、0、负数均拒绝。省略所有次数参数仍默认 1 次；有效固定次数仍优先于区间参数，与原有优先级一致。
4. 未指定固定次数时，区间须同时提供最小值和最大值，两端均在 1~100；保留原有颠倒端点自动交换的便利。先校验整个区间，不能先抽样再判断，以免超限范围偶尔侥幸成功。
5. 超限校验在时间容量调整及过去时间过滤之前完成；短时间范围不能掩盖超大的请求参数。合法请求仍保留现有时间容量缩减、过去时间过滤和成功返回格式。
6. 不带 `time_range_end` 的普通提醒继续走原流程，不因无关随机参数新增限制。普通私聊、群聊来源权限、轻量确认及 action 权限不变。
7. 只限制新建批次。既有提醒继续加载和调度，不自动删除、截断或迁移；单次上限不等于用户／会话总任务配额，也不能防止多次合法请求累积。

建议反馈：超限时明确说明“单次随机提醒最多 100 次，本次未创建，请减少次数”。其他无效参数说明具体原因，不把失败说成成功。

100 条可覆盖常见低频场景，例如一个月每天平均 3 次约 90 条；合法请求仍直接执行，不追加询问。这只是单次批量展开保护，不保证提醒之间的真实最小间隔或不会刷屏。

## 3. 实施边界

- 数量常量、参数校验和时间生成前的保护集中放在 `time_utils.py`，不新增通用工具箱或只包一层的模块。
- `ReminderService` 统一执行创建前校验；`ConfirmationRoutes` 在登记随机创建待确认请求前复用纯校验，避免用户确认后才发现明显超限。预校验不随机抽样，真正执行时再次校验。
- 校验失败不能进入写事务或登记调度任务，不生成大列表，不发消息、不建立无效待确认请求。
- 不修改主项目、运行配置、历史、LLM 缓存、存储格式或旧任务；不重启服务、不做真实投递测试。
- 当前不修改使用提示词、Tool 描述或 Tool schema。若随后需要同步这些说明，先展示具体修改前后对比，单独取得用户确认。
- 不增加每日配额、全局任务数限制、频率限制、安静时段或自动拆批；这些属于独立需求。

其他风险另行处理：批次内调度登记和 JSON 保存不是统一事务，失败时的一致性需单独评估；当前“60 秒”只是容量估算，并非每对随机时间点都严格间隔 60 秒。本次不顺带修改这两项语义。

## 4. 轻量验证与交付

使用临时文件、模拟事件和模拟调度器，不连接真实适配器或 LLM。
