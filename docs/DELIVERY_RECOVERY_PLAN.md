# 提醒投递确认与自主补救方案

状态：**仅插件方案已实施，隔离故障验收通过；真实实例验收部分完成。** 初版方案曾建议修改主项目，现已按用户要求撤销该改动，以下以插件现行实现为准。

基线：KiraAI-Reminder-Plugin `4017a9a`（插件版本 `2.2.1`），本地 KiraAI `28ec106`（`v2.34.8`）。本方案只处理提醒到点后交给 LLM 的确认与补救，不处理群聊创建权限、`action_policy`、自主循环会话白名单等用户自主配置。实施前插件测试 65 项通过；当前自动测试结果见文末，仍不能代替真实模型调用验收。

## 1. 目标与成功定义

一次提醒的“LLM 已收到”定义为：**包含该提醒的首次模型调用正常返回**。模型返回空文本或只返回工具调用，也算已处理；是否最终向 QQ 等平台发出消息，是另一条独立的投递链，不在本方案的成功定义内。“事件入队”“进入 `on.llm_request` 钩子”都不能标记为已收到。

目标是：一次性提醒在确认前不丢失；失败或结果不明的提醒可以被同会话、具备相应权限的后续 LLM 发现和审慎处理；没有后续 LLM 调用时，用户仍能在 WebUI 查看状态并手动处理。重复提醒继续保留原周期调度，同时记录每次未确认的触发，不无限累积记录。

## 2. 现状与仅插件确认信号

插件当前 `_publish_immediate_notice()` 只等待 `event_bus.publish()`，而主项目 `publish()` 只把事件放入队列。`scheduler.py` 随后把这一步视为成功，清理一次性提醒。主项目 `on.llm_request` 在真正调用模型之前触发；`on.llm_response` 在模型全部失败时也会收到合成的 `[ProviderError]` 响应。因此，插件不能单凭现有回调准确区分“模型正常返回”和“所有模型失败”。

主项目现有 `AgentExecutor` 在所有模型调用失败时，会先发出 `on.exception` 事件（`source=provider`、`stage=agent_loop`），然后才向 `on.llm_response` 发出合成的 `[ProviderError]` 响应。插件同时监听这两个既有扩展点：可信、匹配 `delivery_id` 的 provider 异常先把该次投递持久化为 `unconfirmed`；只有仍处于 `awaiting_llm` 的投递，才能被正常响应确认。异常记录写入临时失败时，同进程还保留失败标记，避免随后的合成响应误确认。这里不通过解析 `[ProviderError]` 文本判断成功，也不修改 KiraAI 核心。

这个实现依赖上述既有钩子的触发顺序，而非新增主项目字段。未选择模型、异常发生在调用模型之前、插件重载或进程退出等没有确认的情况，超过等待期限后保留为 `unconfirmed`；网络超时也只能视作结果不明，不能断言模型必然没收到。使用真实 `AgentExecutor` 的集成测试覆盖“异常钩子先于合成响应”这一契约；若未来主项目改变该顺序，应重新验收插件。

## 3. 数据与状态机

推荐新增插件私有的 `delivery_state.json`，以会话 ID 和一次触发的随机 `delivery_id` 记录投递状态；原 `reminders.json` 的旧字段、job ID、配置键和既有 Tool 名称保持兼容。每条投递记录至少保存 `delivery_id`、`job_id`、会话、所有者、触发时间、提醒内容快照、是否含 `action`、状态、尝试次数、最近错误和更新时间。内部事件的可信信封带上 `delivery_id`；只有匹配可信来源和已有待确认记录的响应才能确认该次投递。

| 状态 | 含义 | 后续行为 |
| --- | --- | --- |
| `awaiting_llm` | 投递记录已持久化，事件已提交或准备提交，尚无模型结果 | 不删除一次性提醒；超过等待期限转为 `unconfirmed` |
| `llm_received` | 对应模型调用正常返回 | 先持久化确认，再清理一次性提醒；重复提醒只完成本次触发 |
| `failed` | 能确认事件尚未交给模型的本地失败，例如发布前即报错 | 保留待补救记录，供后续 LLM 或用户处理 |
| `unconfirmed` | 模型调用报错、超时、进程中断或其他无法判断模型是否处理的情况 | 不自动重放，提示可能重复的风险 |
| `resolved` | 用户或有权限的 LLM 明确决定忽略、重新安排或完成补救 | 保存决策者、时间及结果，防止再次反复提示 |

一条一次性提醒在 `llm_received` 前仍是未完成任务。先写投递记录再发布事件；投递记录写入失败时不发布事件。正常响应时先将投递状态写成 `llm_received`，再清理提醒。若两步之间崩溃，启动恢复只补做清理，不重新执行。若模型可能已处理、但确认尚未落盘，启动后保留为 `unconfirmed`；不能声称完全“恰好一次”。

重复提醒按触发实例生成不同的 `delivery_id`。未确认的多次触发可按同一 `job_id` 聚合成“漏处理次数、最早/最近时间”的摘要，保留必要的最近实例，避免高频任务令文件无限增长；不得通过静默丢弃未解决记录来达到容量上限。旧版本已过期、没有投递记录的一次性提醒不能推断为成功，也不能升级后全部自动补发；应保留为待人工/LLM 审视的 `legacy_unconfirmed` 情况。

## 4. 后续 LLM 自主发现与处理

插件在后续 `on.llm_request` 中，只向**相同会话且有权查看该提醒的主体**注入简短的未解决摘要；不能把群成员甲的私人提醒暴露给群成员乙。混合发送者批次身份不明确时，跳过自动注入，避免放大现有批次鉴权风险。摘要包含原定时间、失败/未确认状态、是否含 `action`、可用处理工具；不把原始错误堆栈或完整历史反复塞入提示词。

新增 LLM 原生工具用于查询、决策和记录补救结果，工具端再次按原提醒所有者/管理员权限校验，不能只依赖提示词。普通、无 `action` 的明确失败提醒可由 LLM 决定立即补处理、重新安排、询问用户或标记无需补救；`unconfirmed` 和带 `action` 的提醒不得无确认地重复执行原动作，LLM 可以提出方案或向用户确认。用户也可以在 WebUI 查看并手动重试/忽略。每次决策有唯一记录，重复工具调用必须幂等。

现有权限规则不让普通的可信 BOT 主体自动管理用户所有的提醒。因此，“用户下一次说话时由其身份下的 LLM 发现”与“自主循环在没有用户消息时主动发现”是两个权限场景。后者若要覆盖用户创建的提醒，需单独设计**仅用于投递补救的委托能力**，默认只对明确开启自主循环的私聊白名单生效；不借机授予 BOT 通用的 `reminder.manage_all`。群聊和非白名单会话不做跨所有者的主动补救。

“后续 LLM 自己发现”依赖该会话之后确实有一次 LLM 调用。对于启用了自主循环且在白名单中的会话，可在既有低频自主检查中附带待处理摘要；其他会话不会因本方案新增主动唤醒。若一直没有后续调用，WebUI 状态仍应保留，不谎称已解决。

## 5. 展示、兼容与范围边界

- 看板增加“等待 LLM / 已处理 / 失败 / 未确认”的清楚状态及手动操作；现有 API 路径和字段保留，可增设专门的投递状态 API。`list_reminders` 应能区分过期但未确认的任务，不能仍显示为普通活动中。
- 不改变 `group_create_policy`、`action_policy`、`allowed_sessions` 或 `autonomy_mode` 的用户选择；不新增不受控的自动重试；不把“LLM 正常返回”等同于“QQ 发送成功”或“用户看到了提醒”。
- 不调整提醒正文、`action` 的原有含义或普通时间/重复规则；不在此变更顺手修 `/r all`、混合批次权限、外部 CDN 等独立问题。但补救状态暴露必须遵守现有权限，并对混合批次采取保守跳过。
- 新增代码注释使用英文。仅修改插件；不要改动或清空用户现有提醒数据。测试使用临时目录和假模型/事件总线，真实实例验收在用户确认后进行。

## 6. 分阶段实施与验收

1. **插件确认信号**：结合既有 `on.exception` 与 `on.llm_response`；测试正常文本、空回复、工具调用、全部模型失败，以及无默认模型时不产生误确认。超时/连接异常不能被误判为“确定未送达”。保持主项目代码不变。
2. **插件投递账本**：新增持久化状态、随机关联 ID 和启动恢复；先写记录再入队，只有可信且匹配的正常模型响应才确认。测试入队失败、模型失败、超时、热重载、两次文件写入之间崩溃、重复触发和旧过期提醒。
3. **自主补救入口**：添加权限受控的查询/决策工具及下一次 LLM 请求中的摘要注入；测试同会话不同所有者、混合发送者、无 `action`、含 `action`、`unconfirmed`、重复决策和无后续对话。
4. **WebUI 与真实验收**：展示状态和手动操作；测试页面/API 认证与权限、插件加载/停用/热重载、一次正常模型处理、一次明确失败、一次结果不明。只有日志或可观察结果证实的项目才记为真实验收。

每阶段分别运行插件测试和主项目相关测试，并检查 `git diff --check`；不以“65 项旧测试继续通过”替代新增故障场景测试。任何阶段如发现需要改变权限或自动动作策略，先暂停并重新确认范围。

## 7. 实施结果与待验收

用户已确认上述成功定义、结果不明与 `action` 不自动重放、私聊白名单内自主补救的边界，并进一步明确只希望改插件。先前主项目字段改动已通过新的 revert 提交撤销；实际功能只保留在插件：

- 插件监听主项目既有 provider 异常与模型响应钩子；失败状态不能被后续合成响应误确认。新增真实 `AgentExecutor` 钩子顺序测试，无需新增核心字段。
- 插件新增 `delivery_state.json` 投递账本与可信 `delivery_id`；首次模型正常返回才确认。投递记录写入失败时不发布；确认前保留一次性提醒；过期旧提醒保留为 `legacy_unconfirmed`，不自动重放。
- 同一任务在投递期间被编辑时，新版本不会被旧版未确认记录合并；旧版迟到的确认不会清理新版本。启动恢复会立即识别无投递记录的过期提醒；正常运行期间留出五分钟窗口，避免恰好到点时抢在调度器之前误标为历史未确认。
- 后续同会话、权限允许的 LLM 能看到简短待处理摘要，并通过 `list_delivery_issues` / `review_delivery_issue` 查询和处理。结果不明或含 `action` 的记录不允许 LLM 自动重试或直接忽略；WebUI 手动重试前会提示重复执行风险。暂停、删除或已修改的原提醒不能重试，迟到的旧确认不会删除已编辑提醒。
- WebUI 增加投递状态和手动处理入口；新增 `GET /deliveries/{session_id}` 与 `POST /deliveries/{decision}`。未改动现有提醒配置和用户运行数据。
