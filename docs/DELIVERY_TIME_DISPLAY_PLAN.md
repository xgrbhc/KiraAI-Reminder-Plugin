## 问题与范围

- 投递区直接显示 `issue.reminder.time`，对重复提醒而言是开始时间与周期锚点，不是本条投递的触发时间。
- 投递账本已保存实际尝试的 `created_at`。身份迁移保留原周期时间，不能为修复显示就重写提醒计划。
- 查询 Tool 和本轮临时摘要也存在原时间语义不明确的问题；模型称“记录太久远所以不能清理”并非实际权限规则。无法仅凭截图确认当轮工具是否调用。
- 只修改插件。身份与来源权限、原调度计划、真实数据、自定义提示词、主项目与缓存均不改变；按最终确认方向允许 LLM 忽略投递问题，历史异常不再阻塞新的真实周期，不自动重试或批量清除旧记录。

## 时间规则

| 情况 | 主时间 | 补充信息 |
| --- | --- | --- |
| 正常尝试且时间可靠 | 触发时间：本条投递的 `created_at` | 不等于模型已处理或平台发送成功 |
| `legacy_unconfirmed` 或零次尝试 | 原定时间：快照 `time` | 实际触发时间未知；不使用补建日期 |
| 正常记录但触发时间缺失／无效 | 原定时间：快照 `time` | 实际触发时间未知；不代入其他日期 |
| 同一未处理周期记录合并后续触发 | 原投递触发时间保持不变 | 有有效字段时另显示最近周期触发 `latest_due_at` |

显示精度沿用分钟；不转换浏览器时区，明确偏移保留。格式化只读，不调用 API、不修改状态。多次周期触发合并时，不把最近未再次发布的周期误说成新的投递尝试。

## 新增需求：投递记录与原待办分开处理（待确认）

用户希望提高 LLM 在投递层的自主决策权限，前提是不因此修改原待办或重复计划。

- 现有 `dismiss` 不只是处理投递账本：对一次性提醒会调用清理，并且重启时的协调也会继续执行该清理。不能只放宽入口权限而保留这些副作用。
- 建议允许获准主体自主忽略失败／未确认／旧补建的单次投递问题，不按记录年龄限制；只记录处理决定，保留原提醒、重要标记及调度计划。不允许借此处理其他用户的记录。
- 延后检查继续仅影响投递记录，不清除记录、不自动唤醒。
- 重试会重新执行实际任务，可能重复发送或执行动作；成功回执还可能按原生命周期清理一次性任务。因此“自主忽略”与“自主重试”不能视为同一种低风险操作。本轮建议不扩大重试权限。
- 周期记录忽略后，后续周期继续按原计划处理。过期一次性记录保留后，不自动补发；页面不能把保留记录误报为仍有未来调度。还须防止协调逻辑重新生成同一已忽略异常。
- 尚未实施入口权限、账本处理、协调清理、任务统计或模型文本变更。需先确认处理边界，再展示相应工具说明与返回值的完整对比。

## 最终确认方向：信息记录层，仅查询与忽略

本节取代前述保留重试／延后的候选方案。功能方向及下列模型文本均已向用户展示并获得明确确认（2026-10-06）；仅实施本节内容，不额外修改默认或保存的使用提示词。

### 行为与兼容边界

- 保留 `list_delivery_issues` 与 `review_delivery_issue` 名称，后者仅支持忽略。不新增 Tool、不改变来源与身份校验、管理员适配器范围、自主模式或群聊确认规则。
- 移除投递区的重试入口及投递处理的 retry／defer 能力；旧客户端或旧模型参数收到拒绝，不进行隐藏重试或延后。WebUI 原提醒的编辑、删除和重要确认不改变。
- 忽略 failed／unconfirmed／legacy_unconfirmed 只把投递问题标记为已处理，保留原任务、重要标记和未来计划。处理中 awaiting_llm 不允许忽略；不得假定未确认就没有执行。
- 忽略不得调用一次性提醒清理；启动协调同样不得因已忽略记录删除原任务。正常成功回执结束一次性任务的原生命周期保持不变。已删除的旧任务不从备份自动恢复。
- 原任务仍保留时，需要保留必要已处理标记，防止重载或历史清理后把已忽略的旧异常再次补建。旧 review_after 不再作为新摘要的延后控制，不修改自定义配置。
- 历史失败／未确认不阻止新周期投递；尚在处理中的同一次请求保留防重复保护，不自动重放旧周期。周期异常可在账本层汇总，新的周期仍有独立回执，晚到的旧回执不得误确认新周期。
- 原待办不因历史异常被算成停止运行。保留的过期一次性任务不能被算成有未来调度；仅派生显示状态，不把显示字段写回原任务。
- 是否补做由 LLM 根据上下文自主判断，需要时通过现有工具创建单次任务；不强制创建替代提醒，不自动复制周期计划，不把更换入口当作消除重复执行风险。
- 初次事件发布的既有故障保护、损坏数据保护、正常回执规则与原调度频率不随本次移除补救按钮而改变。
