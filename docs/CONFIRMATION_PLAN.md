# 第 3 阶段：待确认操作与真实发送者确认

日期：2026-10-04。状态：用户确认方案并补充“避免繁杂流程”；已实现轻量确认，自动化验收结果见第 7 节，真实群聊验收待用户重载后进行。

依据：`REQUIREMENTS.md`、`GROUP_IDENTITY_PLAN.md`。第 2 阶段已有用户简单运行测试反馈，未据此认定真实多人群聊、跨适配器及安全边界全部验收完成。

## 1. 检查结论

- 多人批次的普通创建已支持按来源归属；查看、修改、删除和动作设置目前仍拒绝，不具备跨轮确认。
- 现有重要删除令牌校验主体与权限，但不核验真实确认消息。当前测试使用同一个用户事件申请令牌并立即确认，仍能删除；身份正确不等于用户确认。
- 先取消重要标记再删除可以避开重要删除令牌；自主跟进的关闭／替换清理也没有检查重要标记。仅新增确认 Tool 不能宣称重要删除已无旁路。
- 目标提醒可能在等待期间被用户、WebUI 或调度器修改／清理。确认时必须检查当前目标，不能仅在请求创建时鉴权。
- 原始 `im_message` Hook 在合批前提供真实发送者，足以记录确认，不需要修改主项目。核心聊天插件还会把唤醒词转为 `is_mentioned`，不能把这种后续唤醒当成原始 @／回复证据。
- 群聊 Tool 结果进入群聊模型上下文，可能被模型展示给全群；确认不是私密通道，也不能撤回已经进入上下文的内容。

分析依据：插件 `main.py` 的用户 Tool／快捷命令／Web API 入口，`reminder_service.py` 的令牌及写事务，`delivery.py` 的补救规则，`autonomy.py` 的清理流程；主项目的消息事件、消息处理器和默认聊天 Hook 只读核对。

已运行隔离用例 `test_important_delete_requires_actor_bound_confirmation`，1 项通过。其结果证明现有令牌可在无新确认消息的情况下被同主体消费，不是新方案的通过证据；测试未操作真实提醒。

## 2. 已有约束

- 只改插件，不改主项目、合批策略、历史、运行时缓存或全局接口。
- 普通多人个人提醒在既定权限检查通过时仍可自动创建；LLM 可自主先询问。
- 其余多人用户提醒操作绑定选定来源，由 LLM 自然询问；插件不固定发群消息。
- 真实事件决定身份、适配器、会话及权限；来源标记和模型自报“已确认”均不授予权限。
- 请求有效期 5 分钟，内存保存；停用、热重载及重启清空，不自动恢复或重放。
- 群聊确认必须指向当前机器人；不同用户分别确认，不默认采用最后发言人。
- 确认不能放开 `action_policy`，也不能把聊天用户变成 Web 管理员或可信 BOT。

## 3. 已采用的轻量交互

### A. 普通确认与歧义

- 同一用户、同一适配器／会话／机器人仅有一个普通待确认请求时，接受独立正文“确认”或“同意”。
- 有多个请求时必须带请求编号，例如“确认 ab12cd34”；一次只确认一项。
- 删除重要提醒要求明确的“确认删除”；唯一请求无需编号，多项时才附编号，不能用笼统“好的”批准删除。
- 接受独立正文“取消”，但也只针对唯一请求；多项时需“取消 请求编号”。取消不执行操作。
- 只读取本条原始消息的直接文本，不从引用、转发、图片、历史或模型输出提取确认。否定、疑问、条件句、长段文字中的确认词不匹配；解析不确定时让模型重新询问。

这是一组有限的授权回复，不新增 `/r` 命令体系。LLM 仍自然询问并说明需要如何回答。

用户体验约束：只确认确实需要确认的操作；已有准确目标无需反复查询，同一操作不串联两轮确认。轻量交互不省略后台身份、权限和一次性执行检查；这部分不增加用户输入步骤。

### B. 群聊查看的可见范围

- 请求查看提醒／投递时，工具先返回无私有详情的请求编号和询问指引。
- 指引明确要求 LLM 说明“确认后将在本群查询，内容可能展示给群成员”。用户确认授权本次查询，不授权其他用户或其他会话查询。
- 不自动私聊、不跨会话搬运提醒、不承诺 Tool 结果仅用户本人可见。需要私密管理时使用现有认证 WebUI。
- 插件无法独立保证 LLM 真的完整发出提示；此限制须写入使用说明并做真实交互验收。

### C. 重要标记的保护

- 聊天端取消已有重要标记也要求真实确认，包括私聊，防止模型先取消标记再直接删除。
- 重要删除在私聊同样补上原始确认核验；普通私聊的创建、查看、编辑、暂停／恢复不新增确认。
- 自主关闭／替换若要清理重要跟进提醒，拒绝这一清理操作并说明需要显式处理；不能在另一条清理路径绕过。正常到期回执清理不是手动删除，保留其原有语义。
- 已认证 WebUI 保留页面确认框及重要删除令牌流程，不要求管理员再到聊天确认。

## 4. 请求绑定与状态

待确认记录保存不可变副本：随机请求编号、操作类型、完整规范化参数、所选用户、适配器、会话、机器人、原始请求来源、创建时间、截止时间，以及需校验的目标快照。

状态转换：`等待确认 → 已获真实确认 → 已消费`；也可终止为取消、过期或失效。执行前先一次性消费，失败或取消不恢复为可重试，避免不确定结果被重复执行。需要重试时重新建立请求。

- 确认消息必须是请求创建后新观察到的消息，不能重用原请求批次里的“确认”。
- 建议确认 Tool 只在包含该真实确认消息的当前批次中执行，不能在后来的无关聊天里悄悄兑现旧批准。
- 将确认记录绑定原始消息与发送者；即使确认又被多人合批，也不用合批最后发言人的身份。
- 每项请求仅可消费一次；异步锁保护记录和消费，防止两个 Tool 并发重复执行。
- 相同来源与相同参数的重复申请复用未完成请求，不能因模型重复调用刷出一串编号或延长有效期。
- 上限为总计 100 项、每个用户／适配器／会话／机器人 10 项、规范化参数 4096 字符、确认直接文本 200 字符。目标快照最多 100 条、序列化 65536 字符；按需查询最多返回 20 项。达到上限拒绝新增，不挤掉仍有效的请求。
- 不设置新的后台轮询任务；创建、查询、观察和消费时做有界清理，过期检查始终生效。

## 5. 入口覆盖与工程分工

| 入口 | 本阶段处理 |
| --- | --- |
| 普通多人创建 | 保留自动创建；混合权限但选定用户本身获准时建立待确认请求。 |
| 多人查看、编辑、暂停／恢复、标记、删除、设置 action | 有效 `source_ref` 绑定所选用户；生成待确认请求，不先返回现有私有详情。 |
| 重要删除及取消重要标记 | 聊天端统一核验真实确认；重要删除确认覆盖普通混合批次确认，不无意义地询问两遍。 |
| 投递查看／处理 | 多人时确认所选用户；继续限制结果不明／有 action 的重试与忽略，不能用聊天确认绕过 WebUI 限制。 |
| 旧 `confirm_delete_reminder` | 保留入口兼容，但不能仅凭旧令牌直接执行；走相同的真实确认和目标校验。 |
| 自主意图 Tool | 保留现有管理员／可信 BOT、白名单与模式限制；多人批次仍拒绝，不借本轮扩展自主意图授权产品。重要清理补上保护。 |
| 快捷命令 | 保留原始发送者直接操作；重要删除／取消重要标记共用保护，不增设新的命令式功能。 |
| WebUI API | 保留已认证管理职责及页面确认交互；目标失效或变化明确反馈，不能返回“已删除 0 项”的伪成功。 |

- 新增独立 `confirmation.py`：状态、边界、消息解析、证明绑定与一次性消费；不承担提醒持久化或调度职责。
- 新增 `confirmation_routes.py`：集中处理待确认路由及调用共享服务；`main.py` 不逐个复制业务分支。
- `message_sources.py` 提供最小的来源校验复用接口，不复制原始消息或扩展到整段历史。
- `main.py` 保留装饰器和薄入口，增加原始消息观察 Hook、固定注册的 `list_pending_reminder_requests`／`confirm_reminder_request`；查询也是按需且有界，不每轮注入待确认表。
- 原用户 Tool 增加可选 `source_ref`，共用路由辅助方法，不逐个堆砌重复状态逻辑。
- 通过 `CheckedReminderStorage` 在原有存储事务内检查目标快照，`ReminderService` 继续检查当前权限并执行原操作。必须同时检查随机批次成员，不只检查第一条；不在锁外检查后再单独写入。
- `DeliveryTracker` 补救路径在自己的事务内校验投递记录状态／快照；关联提醒也需重新核对，不能声称两个 JSON 文件天然具有跨文件原子性。
- 投递处理按“提醒读锁→投递写锁”固定顺序检查，清理前释放读锁；实际重试发布时再次拒绝已变化的提醒，不把新增 action 当作原批准动作。两文件仍不是持久化的跨文件事务。
- 可信确认凭据只由插件内部创建并验证，不暴露 `confirmed=true` 之类可让模型替换的授权参数。
- 静态 schema 的部署变化会改变工具定义，正常 Tool 返回会增长历史；本阶段不承诺零 Token 成本或固定缓存命中率。

## 7. 实施记录与真实验收

- 新增 2 个固定 Tool 和 1 个原始消息 Hook，当前共 19 个 Tool、7 个 Hook；WebUI 页面和 API 数量不变，无新依赖或后台轮询。
- 普通个人提醒的既有自动创建检查保持；混合权限但所选用户获准时，改为待确认而不是永久拒绝。内部／未知来源混入时仍不自动创建。
- 多人用户 Tool 的来源与确认路由统一实现。重要删除及取消重要标记也覆盖私聊；旧确认入口桥接到真实批准，WebUI 保留原令牌流程并拒绝已变化的目标。
- 自主意图仍不支持多人来源选择；关闭／替换不得清理重要跟进，拒绝关闭清理时不提前把意图标为关闭。此改动不构成两个存储文件的事务保证。
- 原始确认 Hook 使用 `HIGH + 1`，先于主项目内置聊天唤醒词处理观察消息，不更改事件或发送固定消息。使用适配器原始 `is_mentioned` 字段，未提供该能力时保守拒绝群聊确认；其他插件若提前停止或改写原始事件，仍可能影响观察，此时不能绕过验证。
- 重要删除唯一请求回复“确认删除”即可，普通请求回复“确认”／“同意”；多人各自唯一请求可独立确认。模型本轮未消费请求时，仍须在有效期内重新发确认；不会在之后无关聊天中静默执行。

真实验收建议：用户重载／重启 Kira 后，在专用测试群创建非重要测试提醒；多人合批时请求查看或暂停，回复 @／回复机器人“确认”，检查只执行一次。再用专门的重要测试提醒验证“确认删除”、他人不能确认及取消重要标记保护。最后验证原私聊普通创建、WebUI 删除和重载失效。不用真实重要事项或实际自动动作做验收。

自动化结果：插件 220 项通过，主项目插件页面认证／重载／配置相关 18 项通过，Python 合计 238 项；Node 前端 17 项通过，编译和 Git 格式检查通过。测试使用临时文件和模拟原始事件，不连接真实适配器、LLM，也不代表完整生产验收。保留 Starlette、Authlib 两条依赖弃用警告。本轮没有自动提交、推送或重启服务。
