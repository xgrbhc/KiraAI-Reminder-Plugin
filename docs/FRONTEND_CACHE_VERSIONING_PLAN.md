# 前端资源缓存与发布一致性方案

日期：2026-10-13。基线：已发布的插件 v2.3.1。

**状态更新（2026-10-24）：v2.5.0 候选版已实现构建期资源指纹及只读检查。** 7 个直接资源引用均已覆盖；`.gitattributes` 保留被计算指纹文件的准确字节，避免 Windows 换行转换导致归档内资源与指纹不一致。已验证资源哈希及宿主静态路由，旧缓存的真实服务器升级仍待部署验证。下文保留原设计与验收建议，不代表所有缓存来源都已解决。

## 1. 已确认的现象与证据

- 页面初始可打开，会话列表可读取；选择有投递问题的会话后，插件内容整体消失。
- 浏览器实际报错为 `TypeError: deliveryTimes is not a function`。新版 HTML 在投递区域调用该函数，旧版 JS 没有提供它，因此只有渲染此区域时才暴露问题。
- 用户复制的服务器插件声明为 v2.3.1，79 个源码／前端资源文件与发布版一致。复制的数据可解析；匿名化后保留相关结构，18 条待办与 2 条投递问题在隔离浏览器中正常显示，两个用户筛选也正常。
- 混用新版 HTML 与旧版 JS 可在隔离环境复现相同白屏。用户普通强制刷新未恢复；在开发者工具中禁用缓存后刷新恢复，说明缓存参与了实际故障。
- 上述证据不能确认旧响应具体来自浏览器哪一级缓存或中间缓存，但足以说明：磁盘代码已更新，不等于浏览器执行的所有资源都已更新。不能据此清空任务数据或放宽提醒权限。

## 2. 目标与原则

1. 新 HTML 引用对应的新资源；更新内容后，资源请求地址自动变化。
2. 未变化的资源地址保持稳定，允许宿主按原策略复用缓存；不能为解决白屏把所有资源永久禁用缓存。
3. 只使用插件内相对资源，不引入 CDN、运行时联网、Service Worker、前端自动轮询或额外用户操作。
4. 不依赖用户打开 F12、清缓存或手动编辑文件；普通安装仍不要求 Node/npm。
5. 保留现有脚本加载顺序、样式覆盖顺序、页面认证与 API 权限，不改变 LLM 提示词、历史或输入缓存。
6. 本次不夹带投递摘要降频、提醒处理权限调整、页面整体重构或主项目升级。

## 3. 建议选择：构建期内容指纹 + URL 参数

保留现有源文件名，通过开发侧脚本自动为 `index.html` 的资源引用附加指纹：

```html
<!-- Current reference -->
<script src="./app.js"></script>

<!-- Proposed reference; the fingerprint is illustrative, not the actual digest -->
<script src="./app.js?v=9a10bc22de33"></script>
```

- 使用文件内容的 SHA-256 前 12 个十六进制字符作为资源标识；它用于区分内容，不作为安全完整性校验。
- 不使用时间戳、随机数、每次页面打开的 Date.now() 或人工递增常量。相同内容生成相同地址，变更内容才改变地址；不把资源指纹与插件发行版本号强绑定。
- 脚本重复运行应幂等：替换本脚本管理的参数，不重复追加 `?v=` 或修改其它 HTML 内容。未知引用、路径越界、缺失资源等情况应报错，不能输出一半更新的入口文件。
- 先校验全部资源，再一次写入更新后的 HTML；不要在插件启动或处理消息时生成、写入指纹。
- 增加只读检查模式，用于检查引用是否与文件内容一致；脚本本身只依赖 Node 内置模块，不要求安装 npm 依赖。

### 覆盖范围

当前 HTML 的 7 个直接资源引用均纳入检查与指纹管理：

- `app.js`、`i18n.js`、`style.css`。
- `vendor/vue.global.prod.js`、`vendor/tailwind.min.css`。
- `vendor/outfit/outfit.css`、`vendor/fontawesome/css/icons.min.css`。

不能漏掉 Tailwind 产物：新增样式类后它也会变化。第三方文件未变化时，指纹不变，不因插件小版本更新而强制重新下载全部依赖。保留 Vue 在应用脚本之前、翻译在 app.js 之前、自定义样式在 Tailwind 之前的现有顺序。

本轮不重写 vendor CSS 内部的字体 URL，不手改上游生成资源；当前固定字体内容没有本次故障涉及的变化。未来升级字体或图标包时，必须同时评估内部字体 URL 的版本化，不能仅改变入口 CSS 地址就宣称覆盖了所有子资源缓存。

### 跨平台字节一致性

内容指纹不能依赖开发者的 Git 换行设置。拟为参与指纹的自有文本文件明确 LF 检出规则，并让生成脚本使用确定性输出；保留已有 `web/vendor/** -text` 的原字节保护。只处理相关文件，不批量改写整个仓库。

验收时检查 Windows 与 Linux 检出后得到相同指纹。不得因生成时间、绝对路径、机器名或换行不同产生无意义的新地址。

## 4. 缓存与发布边界

- HTML 是入口，应及时重新校验或按宿主管理页面策略禁止缓存。对照截图标注的 Kira v2.33.1，核心给 HTML 设置 no-store，但插件 JS/CSS 没有同样的统一强制策略；本次不修改核心响应头或要求用户升级主项目来解决插件问题。
- 带指纹的查询参数可以避开遵循完整 URL 作为缓存键的旧资源缓存；若部署的代理刻意忽略查询参数，则本方案不能保证生效，需要实际响应验证或改用带指纹的文件名。
- 同一路径加参数并不保证服务器永久保留旧内容：部署后请求旧参数仍可能读取该路径的新文件。因此本方案不将这些地址宣传为永久不可变，也不新增 immutable 或公共长缓存响应头。
- 宿主的认证与私有响应缓存规则保持原样，不能为了缓存命中把管理页面或用户 API 数据开放给共享缓存。
- 前端文件应成套更新，文件复制完成后再重载；不能只复制 index.html 或 app.js。已打开的旧页面不会因后端重载自动获得新脚本，仍应正常重新进入／刷新页面；本方案的目标是无需额外清缓存，而不是浏览器无需刷新就热替换 JS。

### 与完整构建方案的取舍

Vite 等完整构建工具可生成带内容哈希的文件名，并在部署期间短期保留旧资源，提供更强的版本并存保障。但当前插件规模小，采用 URL 参数方案可保留现有代码与分发结构，无需新增 dist 目录或迁移前端框架。

若未来需要 CDN、自定义强缓存、多实例滚动发布或旧资源长期可用，再单独讨论带哈希的物理文件名与发布清理策略，不把它们夹带到本轮修复。

## 5. 拟实施的文件与开发流程

- 新增轻量指纹同步／检查脚本，建议位置 `web/sync-resource-fingerprints.cjs`；具体命令在实施时确定，当前不存在此脚本。
- 更新 `web/index.html` 的上述引用，不改组件模板、文字或业务判断。
- 对接现有 `web/build-assets.cjs`：vendor 构建及 asset-manifest.json 写完之后，再同步入口指纹；保留版本固定、许可和产物校验。
- 在 `web/package.json` 提供开发侧同步／检查入口；其独立构建包版本不随插件发行版本随意修改。
- 明确自有文本文件的换行规则，更新前端维护文档。
- 调整相关测试和隔离预览，不修改插件后端及主项目运行代码。

修改 JS 逻辑、翻译或 style.css 后，仍不需要重建 Tailwind，但需要同步资源指纹。修改 Tailwind 类或依赖时，先按现有规则构建，再同步指纹。同步检查须纳入回归，不能依赖开发者记住逐个修改 HTML 中的值。

普通用户直接使用已提交的完整资源，不执行生成命令。本方案不决定下一个发行版本号；实施验收后，是否发布由用户另行确认。

## 6. 验证计划

### 自动化检查

- 引用数量、相对路径、加载顺序及 MIME 类型保持正确，所有资源可以读取。
- 所有受管理引用的指纹与文件内容一致；重复生成无差异，检查模式不写文件。
- 单个资源改变后，仅对应指纹改变；没有变更的固定资源地址不变。
- 临时夹具覆盖缺失文件、非法／越界引用和重复参数，拒绝失败后入口文件仍完整。
- 更新 `tests/test_local_assets.js` 等文件路径断言：先解析 URL 的路径，再读取文件；不能把 `?v=...` 当作文件名，也不能只去掉参数却不检查指纹。
- 更新 `tests/test_contracts.py` 的页面引用、CSS 类型和资源访问断言，实际请求保留参数。
- 更新 `tests/dashboard_server.py` 的桥接注入匹配方式。当前靠精确匹配无参数的 i18n.js 标签，增加指纹后必须仍能注入模拟桥接；不改变真实主项目的桥接。
- 保持 vendor 原有哈希／许可检查和提醒前端交互测试，不减少校验来使新引用通过。

### 隔离浏览器检查

现有预览统一 no-store，不能直接作为升级缓存测试的证据。需新增仅测试使用的同源缓存场景：

1. 缓存开启，先加载旧版页面与 JS，确认旧资源已缓存。
2. 切换到新版成套资源，保留原浏览器缓存；正常刷新／重新进入页面，不勾选禁用缓存。
3. 加载含投递问题的会话，确认新版 JS 被使用、记录正常显示，不再报 deliveryTimes 缺失。
4. 验证全部用户、指定用户、无投递问题及有投递问题；观察中英文、样式顺序、按钮与窄屏布局。
5. 检查不变资源仍具备缓存复用条件；不把特定宿主是否允许缓存误当作插件能控制的保证。

仅使用虚构记录和临时文件，不读取真实凭据、不调用真实 LLM、不测试真实重试／忽略／删除操作。测试完成关闭页面和服务器。

## 7. 后续执行与验收

1. 用户确认实施本方案后，先实现指纹脚本、入口引用和相应测试。
2. 完成静态资源／接口回归及带旧缓存的隔离浏览器验证；真实服务器由用户按原方式更新并普通刷新检查。
3. 确认无需 F12 禁用缓存即可显示投递问题，再讨论提交、推送与发行；不自动沿用上一次发布授权。

验收重点是正常缓存条件下升级后资源一致，不是仅在空缓存或禁用缓存时页面正常。若失败，先定位 HTML 引用、实际 JS 响应和缓存来源，不能清任务数据或放宽权限来绕过。

资源变更不做数据迁移。需要回退时应使用同一发布版本的整套前端文件及引用；禁止只回退 HTML 或单个 JS，禁止移动已发布标签。
