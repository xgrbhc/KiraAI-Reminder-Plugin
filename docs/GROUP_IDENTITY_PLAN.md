# 群聊来源识别与适配器权限方案

日期：2026-10-03。状态：第 1 阶段已实现并通过自动化测试，待真实加载验收；第 2～4 阶段尚未实施。依据：`REQUIREMENTS.md` 中用户确认的 1B、2A、3A、4A、5A。

## 1. 目标与现状

群聊多人消息合批后，LLM 默认收到拼接的消息文本，Tool 收到完整事件。插件当前使用最后一条消息确定身份，可能误记所有者或借用管理员权限。

目标是按需向 LLM 提供当前批次的消息来源，让插件按真实事件校验身份；保留三种群聊策略，支持不同适配器，并避免每轮修改提示词和缓存前缀。

## 2. 已选行为

| 场景 | 处理 |
| --- | --- |
| 单一用户、相同事件来源 | 保留现有交互，无需新增来源查询或身份确认。 |
| 多位用户分别提出需求 | 分别选择来源、鉴权及操作；一个失败不代替其他用户作决定。 |
| 多人批次中的普通个人提醒 | 在来源及自动创建权限检查通过后创建；LLM 可自主选择先确认。 |
| 多人批次中的查看、修改、删除或 `action` | 先记录待确认请求，由 LLM 询问对应用户；确认后重新鉴权。 |
| 来源缺失、歧义或标记失效 | 返回可理解的原因与下一步；不得退回“最后发言人”。 |
| 来源查询或模型步骤不足 | 本轮可以结束，不绕过来源与确认检查。 |

普通个人提醒指为选定用户创建的、无 `action` 的提醒；创建成功不表示平台消息已送达。用户已接受 LLM 偶尔选错来源的归属风险，尚不能据此宣称意图归属绝对准确。

## 3. 按需来源查询

- 新增只读 Tool（建议名 `list_message_sources`），只读取当前事件的消息，不查询历史或其他会话。
- 返回当前批次的临时 `source_ref`、昵称、必要的消息片段和来源类型；真实用户 ID 留在插件，禁止输出可信信封密钥或原始 `extra`。
- `source_ref` 绑定本批次与具体原始消息；历史中的标记不能在下一批次复用。缺失身份、来源不可信或数据截断影响定位时明确返回限制。
- 固定注册 Tool 及其 schema，避免按批次动态改变工具定义；无提醒需求时不必调用。
- 多人批次中的用户提醒 Tool 增加可选来源参数。未提供有效来源时，返回“先查询来源”的工具结果，不写数据、不泄露提醒详情。

## 4. 权限与自动创建边界

- 使用所选原始消息构造插件内部请求上下文，读取其适配器、用户、会话及 @／回复状态；不修改原始批次，也不继承其他消息的可信信封。
- 所选用户必须通过现有群聊创建策略。普通自动创建不能仅因模型选中了管理员消息，就绕过同批次其他未获准用户的权限。
- 对普通自动创建使用保守的批次权限检查：潜在用户来源均获准创建时，允许按选定来源创建；批次含未获准用户时，应由拟操作的获准用户先确认。无权限者确认后仍无权限。
- 混合用户与内部事件不能共享 BOT／SYSTEM 能力；用户来源查询不得签发内部主体的可操作标记。
- 查看和修改也必须核验来源与权限，不能只保护 `set_reminder`。确认、恢复投递及重要删除均不能成为绕过入口。

这会使 `all` 模式中的普通创建更流畅；`admin_only` 和 `mentioned_user` 模式遇到不同权限来源混合时可能需要确认，避免以 LLM 的选择作为管理员授权。

## 5. 确认流程

1. 插件保存待确认操作的完整参数、适配器、会话和目标用户，返回请求标记及询问所需的最少信息。
2. LLM 自然询问用户。插件不固定向群里发送确认文本，也不在确认前返回其他用户的私有提醒内容。
3. 插件通过逐条原始消息观察真实用户确认，不依赖合批后的最后发言人或 LLM 自报“已经确认”。群聊确认需指向机器人；同一用户存在多个待确认请求时不能用一个模糊“确认”批准全部。
4. LLM 调用确认 Tool；插件核验真实确认记录，重新检查当前权限及目标任务，然后以保存的参数执行。模型不能在确认后替换内容、目标或动作。
5. 请求过期、取消、任务发生相关修改或已执行时拒绝继续；同一请求只能消费一次。

确认记录优先采用插件内存状态与锁，短期有效；初始有效期建议沿用现有重要删除的时间尺度。停用、重载或重启使未完成请求失效，不自动重放。重要删除仍须明确针对删除目标的确认，避免产生无意义的重复询问。

## 6. 适配器身份与旧数据

- 普通用户身份按“适配器名称＋原始用户 ID”识别；优先读取通用事件／Session 字段，旧数据可从 Kira 的会话标识恢复适配器。
- 聊天管理员及授权用户按适配器配置。管理员跨用户操作时，还须检查目标提醒所在适配器属于其授权范围。
- 本选择针对聊天账号权限；已认证 WebUI 作为部署管理入口，保留其原有管理职责。
- 旧提醒和投递快照的所有者范围应从所属会话迁移，先备份并保持幂等；不能仅凭数字 ID 合并跨适配器身份。
- 旧裸 ID 权限配置缺少适配器范围：仅有一个适配器时可明确迁移到该范围；存在多个适配器时需配置明确范围，不能静默扩展到所有平台。迁移须给出可操作说明并保留旧配置。
- 不增加账号绑定、全局聊天超级管理员或新的适配器运行依赖。

## 7. 工程与缓存

- `main.py` 保留装饰器和薄入口；来源上下文放入独立小模块，权限规则集中在 `permissions.py`，提醒操作继续调用共享服务。确认逻辑确有独立职责时再抽模块。
- 不改 KiraAI 的缓存配置、历史消息或消息处理流程，不拆分／强制刷新主项目群聊批次。
- 普通聊天不附动态来源表；查询结果走正常 Tool 返回，限制消息数量、片段长度和总返回量。不得为获取来源复制整段历史。
- Kira 正常 Tool 结果会进入会话历史，因此此方案有按需 Token 与模型步骤成本；不能承诺零历史增长或固定缓存命中率。
- 固定工具定义和使用规则只在部署／配置变化时改变。实际验收检查未调用时的请求前缀、调用时的返回长度以及缓存与 Token 指标。
- 现有投递恢复提示的系统提示词注入另作缓存检查，必要时改为当前请求末尾非持久上下文，不改变投递确认语义。

## 8. 实施顺序与验收

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 适配器身份、授权范围及旧数据兼容 | 相同用户 ID 在两个适配器中不串权；管理员不能跨未授权适配器管理；旧提醒与配置可恢复。 |
| 2 | 来源查询 Tool、批次标记及普通创建检查 | 单一用户体验不变；多人 `all` 普通创建按所选用户归属；普通成员不能借管理员消息自动创建。 |
| 3 | 待确认操作、原始消息确认与其他入口校验 | 他人不能确认、过期不能确认、重复不能执行；查看／写入／重要删除／投递处理无旁路。 |
| 4 | 缓存检查、提示说明和真实群聊验收 | 无需求不添加身份表；Tool 返回有界；原有静态前缀与历史不被改写；实际缓存指标与交互可接受。 |

每阶段独立验证与提交。测试使用临时数据和模拟 QQ／其他适配器事件，覆盖用户→管理员、管理员→用户、不同 @ 状态、内部事件混合、旧来源标记重用以及多人独立请求；不以真实用户数据进行迁移试验。

## 9. 第 1 阶段交付与验证

- `identity.py` 统一提取事件／Session 的适配器范围，用户的内部操作标识包含适配器；适配器与会话范围冲突时不授予用户权限。
- `permissions.py` 统一使用适配器范围校验用户、授权用户、聊天管理员与目标记录。Tool、快捷命令、投递补救和重要删除确认共用此规则；已认证 WebUI 保留原有管理能力。
- `admin_users`／`authorized_users` 使用 `适配器名称:用户ID`，区分大小写。`legacy_acl_adapter` 只绑定旧裸 ID，不能扩大带范围条目的权限；多适配器不自动推断，未明确归属的裸 ID 不获得额外权限，普通私聊自用及 `all`／`mentioned_user` 原有资格仍按各自规则判断。
- 仅有一个已配置适配器（包含停用项）时，首次加载先备份插件配置，再原子保存其名称到 `legacy_acl_adapter`。保存成功后才启用旧权限；后续新增或更换适配器不会静默改绑。
- `migration.py` 将提醒与投递快照升级到 identity schema v3，新增 `owner_adapter_name`／`created_by_adapter_name`，保留已有 v2 所有者及其他字段。先读取两份数据、建立所需备份，再分别原子写入；两文件写入不是跨文件事务，失败必须停止加载，重新加载可继续幂等迁移。
- 首次迁移保留 `reminders.pre-identity-v3.backup.json`、`delivery_state.pre-identity-v3.backup.json`；权限配置保留 `reminder_plugin.pre-adapter-acl.backup.json`。没有对应旧文件或待迁移记录时不生成无意义备份，历史 `pre-v2.2` 备份不变。

自动化验证：使用 Miniconda 的 KiraAI 环境执行插件全量测试，**118 项通过**；保留原有 1 条 Starlette 测试客户端弃用警告。新增测试覆盖跨适配器同号、权限矩阵、配置绑定与歧义、迁移幂等与中途失败重试、投递快照匹配、Tool/API 入口及跨适配器重要删除令牌。测试只使用临时文件，未迁移真实运行数据，未修改主项目代码。

真实验收建议：

1. 重载插件，查看初始化与迁移日志；如提示裸 ID 范围不明确，在插件配置指定 `legacy_acl_adapter` 或把列表改成带适配器的格式。
2. 在原私聊创建、查看、暂停／恢复并删除一条测试提醒；检查旧提醒与 WebUI 看板仍可访问。
3. 若有群聊环境，验证管理员／授权用户资格及当前群聊策略；重载后检查任务没有重复登记。第二个适配器可先用模拟测试覆盖，真实平台验证另行补充。
4. 若需回滚，先停用插件并备份当前文件；配置、提醒和投递记录必须按对应版本成组核对恢复，不能只恢复一个文件。迁移后新增任务不在迁移前备份中，不能直接覆盖丢失。

本阶段不宣称解决多人合批的意图归属；下一阶段新增按需来源 Tool 与批次标记，之后才接入待确认操作。随机任务硬上限、WebUI 资源本地化和其他审查项保持独立范围。
