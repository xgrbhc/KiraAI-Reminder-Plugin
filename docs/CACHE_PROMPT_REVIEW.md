日期：2026-10-04。状态：用户看过完整提示词对比后批准 A+B，代码修复及隔离验证已完成，实施记录见第 5 节；没有修改主项目、保存的配置、历史或缓存，没有重启、调用真实 LLM 或提交。第 3 阶段真实群聊确认及第 4 阶段实际指标对照仍待验收，不能把此前简单运行反馈当成完整验证。第 1 节保留实施前的检查证据，不代表修复后的代码仍有该注入位置。

## 1. 结论与证据

### 1.1 优先修复：动态投递摘要进入系统提示词

插件 `main.py:207` 的 `inject_delivery_issues` 在普通单一来源请求中检查未确认投递，把最多 5 条摘要追加到 `req.system_prompt`，名称为 `reminder_delivery_recovery`。摘要随内容、投递状态和延后时间变化；无异常时不添加。

主项目 `core/provider/llm_model.py` 只按名称迁移 `sessions`、`chat_env`、`time`，并单独处理 `memory`；不会自动迁移插件的恢复摘要。因此当前 `dynamic_prompt_position=latest_user`、`memory_prompt_position=latest_user` 不能解决这块问题。

隔离验证：模拟两次相同历史、相同当前消息、相同静态规则，只改变恢复摘要中的 `test-A` / `test-B`。使用实际 `LLMRequest.assemble_prompt` 后，系统消息不同，摘要未进入最新用户消息，历史内容未改写。这证明存在插件引起的系统前缀变动，不证明每次变化都会导致全部缓存失效，也不等于缓存数据被删除。

建议：保留现有权限、可见条数、延后规则和恢复提醒能力；把摘要作为插件自己的 `Prompt(..., persist=False)` 追加到 `req.user_prompt` 末尾。不借用核心动态块名称，不删除、搬移或改写已有 Prompt，不改主项目。数据应标明为投递记录而非用户新指令，并转义或结构化呈现不可信提醒内容。

主项目 `core/message_manager.py:721` 已按 `persist` 过滤用户输入的持久化内容，适合本轮非持久上下文。仍需用真实组装路径验证最新输入保留摘要、保存到历史的用户消息不包含摘要；仅在系统 Prompt 上设置 `persist=False` 不足以使其移位。

摘要保留在同一轮后续模型步骤中属于预期，不因为不持久化而在首次模型调用后消失。

### 1.2 优先修复：静态使用说明与新工具冲突

`config.py` 的 `DEFAULT_USAGE_PROMPT` 和 `schema.json` 的默认值都要求管理前先调用 `list_reminders`；schema 还写成“查询前先查询”。这可能造成已有准确目标时重复查询，群聊中甚至多出一次查询确认。

当前工具说明已经要求“已有准确 job_id 无需反复查询”，并支持 `list_message_sources`、`list_pending_reminder_requests`、`confirm_reminder_request`，但静态使用说明没有同步。重要删除仍只提示旧 `confirm_delete_reminder` 入口，容易让模型误解为必须串联多轮确认。

建议统一代码和 schema 的默认说明，保留低频主动跟进、可靠时间判断、群聊谨慎、独立 action 权限及诚实反馈，增加按需来源和单次确认规则；不把完整实现细节或身份表塞进静态说明。固定规则只随部署/配置改变，不按用户或批次动态改写。

只读检查当前保存的提示词：1391 字符，包含强制先查询要求，不含两个新来源/确认工具的名称。`_get_usage_prompt` 优先使用保存的配置；因此只改默认值不能更新现有部署。代码与 schema 当前默认文本也不完全一致。

不自动覆盖保存的提示词，不做无法可靠判断的“旧默认自动迁移”；交付统一推荐文本，由用户选择是否在插件高级配置中替换。空 usage_prompt 仍保留禁用该静态说明的原语义。

推荐规则方向（实施时保留完整产品能力说明）：

> 无提醒或确认需求时不必查询。单一来源沿用通常流程；多人或来源不明时按需调用 list_message_sources，只使用当前批次标记，标记不授予权限。已有可靠且准确的 job_id 不重复查询；没有准确目标才查询。工具返回待确认请求时，自然询问一次；唯一普通请求回复“确认”即可，重要删除回复“确认删除”，多项才附编号。收到真实确认后调用 confirm_reminder_request，不替用户确认，也不再次询问同一操作。群聊查询需说明结果可能展示给群成员。权限和 action 限制以工具校验为准，失败不得说成成功。

### 1.3 已符合目标：来源与待确认信息按需提供

- 没有每轮动态来源表或待确认表的注入 Hook；两类查询走固定注册的只读 Tool。
- 来源查询只读当前批次，最多 20 条，昵称 40 字符、片段 120 字符，总返回上限 12000 字符；不完整时明确提示并停止签发可操作标记。
- 待确认查询最多 20 条，返回编号、操作、昵称、确认状态和回复方式，不返回保存的参数或私有目标内容。
- 隔离来源样本：2 条各 120 个 ASCII 字符的消息返回 770 字符，20 条返回 6509 字符。这是字符长度，不是模型 Token 数，也不是最坏情况上限。
- 不建议为了进一步压缩而取消昵称、片段、歧义提示或权限校验，也不新增每轮轮询与强制确认。

Tool 返回仍通过主项目 `AgentExecutor` 进入 `ctx.new_messages`，由 `session_manager.update_memory` 保存。按需提供不是零历史增长；禁止插件自行删除正常工具调用/结果来“修复缓存”。

### 1.4 独立后续项：其他返回内容并非全部有界

`ReminderService.list_reminders` 返回全部可访问提醒和完整 content/action，没有分页或总长度限制；`_list_delivery_issues` 虽最多 20 条，但单条 content 未截断。自主事件正文也包含完整 notes/content 和自主使用说明。

大量任务或超长内容会增加输入和历史成本。但直接截断查询会影响找任务、管理和动作理解，修改消息/任务限制也会改变已有行为。建议单独设计“摘要 + 按需详情/分页”的规则，本轮不顺带改查询契约、存储数据、随机任务上限或自主循环语义。投递恢复 Hook 的全库 reconcile 成本也应独立评估，不在缓存修复中改变其可靠性职责。
