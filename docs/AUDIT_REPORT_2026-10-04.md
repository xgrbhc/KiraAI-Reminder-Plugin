### R1：创建成功不能只表示“记录存在”

复现：假调度器注册时抛出异常；`ReminderScheduler.add_job()` 记录警告后吞掉异常，服务仍返回“已添加”。最终文件有 1 条记录，调度器有 0 个任务。

影响：用户以为已经设置成功，但这次运行中没有对应任务触发。恢复提醒也调用同一注册入口，具有同类风险；恢复路径没有在本轮单独注入该故障。

建议：注册结果必须反馈给服务层。明确区分“已保存并成功调度”和“已保存但调度失败”，或采用明确的补偿策略。不能只有日志警告，不能依赖 LLM 自行从日志猜测。

### R2：原子文件写入不等于业务事务原子

复现：准备一条未暂停的每日提醒和对应假调度任务，让 `_unsafe_save()` 抛出磁盘写入错误，分别调用暂停、删除。

两种情况下，调用均返回错误，磁盘原记录保持不变，但假调度任务已经被移除。这两项复现属于同一个根因，不应计为两个独立架构问题。

原因：调度副作用在 `storage.modify()` 内发生；文件直到退出上下文时才保存。保存失败不能撤销先前的 `remove_job()`。

影响：界面/文件显示仍活动，运行中却不再触发。当前健康检查主要处理调度器停止，不保证修复运行中缺失的单个任务。

建议：统一创建、编辑、暂停、恢复、删除的“持久化—调度”一致性策略。以已提交记录为调度依据，保存失败不能破坏原运行任务；调度失败要可见、可恢复。仅把注册移动到事务外，并不能自动解决另一方向的失败。

边界：不需要为了修复就引入数据库、改变投递确认定义或自动重试真实动作。创建/编辑也有同类源代码风险，但本轮直接注入并证明的是暂停和删除。

### R3：自主规划并发丢失更新

复现顺序：

1. `daily_cycle_job()` 读取自主状态。
2. 假发布回调等待，模拟正常异步消息处理时间。
3. 同时调用 `create_intent()`，新意图已保存，文件中有 1 条。
4. 周期任务恢复，保存第 1 步的旧状态；新意图变为 0 条。

影响范围：启用自主规划及相应周期任务时，可能丢失期间创建/编辑的意图。这不是对普通提醒文件的直接覆盖，也不是所有用户默认都会触发。

`save()` 的锁只保护保存动作，不能让先前独立的 `load()` 与后续 `save()` 组成完整的读改写事务。跟进、随机检查等其他旧快照保存路径也值得一并检查，但本轮直接复现的是每日周期任务。

建议：外部发布结束后，用短暂的 `modify()` 读取最新状态，仅合并本轮实际改变的字段，并检查目标是否仍有效。不要持有整个文件锁等待 LLM 或外部发布。不改变自主规划策略、提示词或权限规则。

### R4：错误返回与实际保存不一致

复现：`update_intent(title="changed", status="invalid")` 返回 status 参数错误，但原标题已经改为 `changed`。

原因：先修改 title/notes，再验证 status/priority；返回错误不等于抛出异常，正常退出 `modify()` 仍会保存。

建议：先把全部参数验证为有效的候选变更，再一次性更新目标；错误路径应保证原记录不变。顺便检查其他事务内先改值、后返回错误的路径，不要无依据地扩大为全部接口都有问题。

### R5：随机提醒的时间精度不一致

复现窗口：`2099-01-01 10:00` 到 `10:03`，请求 2 次。两个 90 秒分段分别确定采样为 10:01:29 和 10:01:30；保存为分钟格式后，两条时间都是 `10:01`，job_id 不同。

影响：同一分钟连续收到两条同内容提醒，体验上像重复触发。现有单次最多 100 次限制仍然生效；这不是绕过次数限制。

原因：`min_interval=60` 用于计算容量，不保证实际采样点相距至少一分钟；秒级采样后又截到分钟。

建议：随机采样与保存/调度使用同一粒度，例如从不重复的分钟槽位采样。是否需要严格“至少间隔一分钟”、窗口太短如何处理，应沿用已有规则或先确认，不能擅自增加复杂确认流程。

### R6：损坏保护只验证到 JSON 顶层

复现：自主状态为合法 JSON，但某会话的 `intents` 是字符串。创建新意图时，`ensure_autonomy_session()` 将它重置为空列表，再保存新意图，原错误字段被替换。

影响：损坏或人工改错的嵌套状态可能被正常写入覆盖，失去后续人工排查机会。没有证明正常有效意图列表因此被丢弃；应与 R3 区分。

建议：各数据文件在读写前做适度结构检查。已知旧格式迁移与无法识别的损坏要区别处理；损坏时保留原文件并说明原因。不要把通用存储类强制限定为一种业务结构，因为它被多个状态文件复用。

## 5. 正向保护验证

补充注入 `os.replace()` 的 PermissionError：保存失败后，旧提醒文件内容不变，临时 `.tmp` 文件清理成功。

这说明现有临时文件、flush/fsync、原子替换方式在此故障点保护了原文件。原本针对不可读文件和无效 JSON 的拒绝写入测试也全部通过。

因此，不建议因 R2 全面重写文件存储。需要补足的是业务状态与调度的一致性，以及 R6 的嵌套结构边界。

## 6. 需要明确的需求，不直接修改

### 重复提醒的日期是不是“首次触发日期”？

观察：设置每日提醒 `2099-01-01 10:00`，按当前 CronTrigger 定义，从 `2026-10-04 00:00` 计算，下次为 `2026-10-04 10:00`。每日规则只使用小时、分钟，没有使用开始日期。

每周、每月、每年也未配置 `start_date`，这是源代码观察，未分别运行探针。不能据此认定是本轮前端或重构造成的退化。

需要选择：

- 输入完整日期表示首次开始日期，之后按周期重复；应补开始日期约束。
- 日期仅用于描述每周/月/年的重复锚点，每日只取时间；应在接口与文档明确，避免用户误解。

建议倾向第一种，但实施前应确认语义；涉及工具描述/提示词的调整仍须先展示对比并获批。
