# Reminder Plugin 需求与规则

状态：需求规则已确认，第 1、2 阶段已实现并通过自动化测试（2026-10-04）；第 3 阶段轻量确认已实现，交付记录见 `CONFIRMATION_PLAN.md`。已观察真实页面读取，第 2 阶段已有用户简单运行测试反馈，完整群聊安全验收仍待补充。本文描述产品目标与行为边界，不代表全部已实现；实现现状以代码和测试为准。群聊来源识别方案见 `GROUP_IDENTITY_PLAN.md`，第 4 阶段代码修复与隔离验证已完成，实际缓存指标和真实交互待验证，见 `CACHE_PROMPT_REVIEW.md`。

## 1. 定位与范围

- 插件为 KiraAI 提供可持久化的时间驱动能力：让 AI 安排未来事项，并在到期时继续处理，而不只是发送固定闹钟文字。
- 服务对象包括私聊用户、群聊中的个人，以及按配置开放给部分或全部群成员的场景；应适用于 KiraAI 支持的不同适配器。
- 自然语言和 LLM Tool 是主要交互方式；现有快捷命令与 WebUI 是辅助管理入口。
- 当前范围是提醒、待办、重复／间隔／随机触发、任务管理、有限的自主跟进和投递状态。跨插件工作流、任意条件触发及“群共有提醒”只是未来方向，不纳入本轮需求。

## 2. 基本行为

- 用户明确提出提醒，或上下文可靠地表达后续跟进意图时，AI 可以调用工具；时间等关键参数无法可靠确定时必须先询问，不得编造具体时间。
- 提醒应保存内容、触发时间、所属会话、创建者／所有者和必要的调度状态；重启后应能恢复未完成任务。
- 支持一次性、每日／每周／每月／每年、间隔和指定时间范围内的随机提醒，以及查询、编辑、暂停、恢复、删除和重要标记。
- 日／周／月／年重复的 `time` 是开始约束与周期锚点，不在执行后改写；不提前触发或新增历史补发。查询／页面的“下次”须来自实际调度，不能持久化、代替投递状态或在任务缺失时自行推算。
- 到期事件应回到 KiraAI，使 AI 能结合上下文决定如何回应；若使用 `action`，必须另行通过动作权限校验。
- 修改或删除前应先定位准确的任务；删除重要提醒必须由用户明确确认，不得由 AI 自行完成确认。
- 工具失败时必须如实反馈，不得把拒绝、参数错误或投递失败说成成功。

## 3. 身份、归属与群聊权限

- 私聊用户可管理自己的提醒；群聊中的用户提醒也归属于具体用户，不因创建于群内就自动归全群所有。
- 群聊创建遵循现有 `group_create_policy`，管理员和 `authorized_users` 在三种模式下均可创建：

  | 模式 | 其他群成员何时可创建 |
  | --- | --- |
  | `admin_only` | 不可创建 |
  | `mentioned_user` | 当前发言人 @ 或回复机器人时，可创建自己的提醒 |
  | `all` | 可创建自己的提醒 |

- 群聊快捷命令始终要求 @ 或回复机器人；此唤醒规则与创建权限分别判断。
- 用户身份按适配器分别识别，相同用户 ID 不自动视为同一人；本轮不增加跨平台账号绑定。
- 用户提醒只允许其所有者管理；聊天账号管理员按适配器分别授权，仅可在授权范围内跨用户管理。自动动作使用独立的 `action_policy`，不得因 `group_create_policy=all` 而自动放开。
- LLM 可以识别意图和候选来源消息，但身份、会话、@／回复状态与权限必须取自可信事件元数据，不得采用 LLM 自报的用户 ID 或消息文字中的身份声明。
- 多人消息被合并时，不得默认把 Tool 操作归给最后一位发言人；无法可靠确认请求来源时，不得执行依赖身份的操作。普通群聊回复和其他明确来源的请求不应因此被整体禁用。
- 来源信息通过只读 Tool 按需获取，不在每次多人合批时自动附加身份表；提醒工具执行层仍须检查来源，防止 LLM 跳过查询。
- 多人合批中的普通个人提醒可以自动创建；LLM 也可自主先询问用户确认。接受 LLM 偶尔选错来源造成归属错误的风险，但不允许借用其他发言人的管理员或内部主体权限。
- 多人合批中的其余用户提醒操作，包括查看、修改、删除以及设置 `action`，须由对应用户确认后执行；确认不能扩大原有权限。
- 一批中多位用户分别提出请求时，逐条独立处理、鉴权和确认，不把整批请求归给同一人。
- 确认询问由 LLM 自然发送；插件保存请求并核验原始确认消息的发送者。未收到有效确认时，不执行待确认操作。
- 确认交互尽量轻量：唯一普通请求可简短回复，多项才区分编号；重要删除明确表达删除同意，同一操作不重复询问。后台安全检查不能变成繁杂的用户输入流程。

## 4. 主动性、可靠性与用户控制

- 自主意图循环默认关闭；启用后仍受会话白名单、运行模式及工具白名单限制。
- 主动任务应低频、可暂停、可解释；群聊比私聊更谨慎，避免骚扰、刷屏或替他人安排任务。
- 提醒投递到模型后，只有相关模型调用正常返回，才能视为“LLM 已收到／处理”；这不等于平台消息已发送或用户已阅读。
- 模型失败、超时或结果不明时，应保留一次性提醒及可检查的投递状态；不能对可能已经执行过的 `action` 盲目自动重试。
- LLM 可按权限查询投递问题，并对明确失败且无动作的记录选择重试／忽略；结果不明或含动作的记录仅可延后检查，重试／忽略须 WebUI 确认。延后检查不等于自动重试或自动唤醒。
- 已存在但不可读取或损坏的数据文件必须保留并报错，不得作为空数据覆盖。
- 文件保存失败不得破坏原运行任务；调度失败不得误报成功，应补偿本次变更。补偿未完整完成时必须明确说明，不能承诺已恢复。

## 5. 工程结构与主项目兼容

- 功能变更前应先明确场景、规则、边界和验收用例；结构重构与行为修复分开实施，不为拆文件而拆文件。
- 修改提示词前，必须向用户展示修改前后对比及影响，取得明确确认后才修改；包括默认／自定义提示词、LLM 工具说明和动态提示文本。提示词位置、角色或持久化方式改变也须说明；一般性的“继续实施”不代替对具体提示词改动的确认。
- `main.py` 保持为插件入口和 Hook／Tool／API 适配层；权限、提醒业务、持久化、调度和自主循环各有清晰职责，避免重复规则与循环依赖。
- 优先使用 KiraAI 公开的插件接口；不得修改主项目代码、猴子补丁全局行为，或依赖未承诺稳定的内部实现。确需特定核心能力时，应声明最低兼容版本并测试。
- 插件的错误、后台任务和资源清理不得阻塞或破坏主项目正常消息处理；加载、停用及配置热重载必须可重复执行且无遗留任务。
- 身份、会话、发送和 @／回复判断应依赖适配器提供的通用事件字段，不硬编码 QQ 号、QQ 会话格式或 QQ 专属 API；适配器差异应集中在边界处理。
- 不为插件引入不必要的主项目或外部服务强制依赖；可选能力不可用时，应有明确的降级、拒绝或错误提示，不得静默误判成功。
- 不得清空或改写主项目的 LLM 缓存、历史消息及静态提示词前缀。每轮变化的信息应按需提供；若需注入提示词，应使用本轮最新用户输入末尾的有界、非持久上下文，不得插入静态系统提示词。工具结果可能进入会话记忆，须限制其内容与长度，并检查缓存和记忆影响。
- 关键规则须有自动化测试，至少覆盖权限矩阵、私聊／群聊、不同适配器事件、失败路径及生命周期；文档、配置说明和实际行为应一致。

## 6. 验收重点

- 私聊、单一发送者群聊在三种群聊策略下按上述权限运行；用户只能管理自己有权管理的提醒。
- 混合发送者批次中，普通成员不能借用管理员或内部主体身份；提醒归属不得默认采用最后发言人，应使用经过事件校验的来源标记。
- 插件加载、配置重载、停用和重启后，任务与后台调度不丢失、不重复登记。
- 到期、模型失败、重要删除及损坏数据均有可验证的结果；对用户展示的状态不超出实际证据。
- 不修改主项目即可加载、停用和热重载；至少以两种适配器形状的模拟事件验证通用身份与会话处理。
- 来源识别方案须验证：不使用该能力时不添加每轮身份信息；使用时工具结果或临时提示有界，且输入 Token、缓存命中和会话记忆变化可接受。

## 7. 已确认选择与实施边界

- 2026-10-03 用户选择：1B（普通个人提醒可自动创建，LLM 可自主询问确认）、2A（多位用户分别处理）、3A（LLM 询问）、4A（适配器身份独立）、5A（管理员按适配器授权）。
- 来源标记的有效范围、确认请求的匹配与过期、旧权限配置迁移和缓存验证方式，在实施方案中明确；不把 LLM 选择的来源标记视为独立授权证据。
- 群共有提醒、安静时段、统一频率预算、条件触发和跨插件编排，属于后续产品设计；不得在修复身份归属时顺带改变现有语义。
- 本次先确认规则并编写实施方案；行为变更须按方案分阶段实现、测试和验收。KiraAI 主项目保持插件外部依赖，不修改其运行代码。
